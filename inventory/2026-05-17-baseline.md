## Inventory 觀察 / 建議

### 題材分佈
1. **CC 工具鏈深度整合踩坑**（候選 1, 2, 6, 9, 15, 16, 17, 20, 27, 34）= 10 個 → 是最強 cluster，blog identity 可定位「跟 CC 重度整合的個人故事」
2. **工具評估 / 否決紀律**（候選 10, 11, 12, 13, 14, 29, 30, 33）= 8 個 → 第二強 cluster，可以建立 「為什麼我評估完不採用 X」系列
3. **個人系統設計**（候選 4, 5, 18, 22, 26, 32）= 6 個 → 較少但每篇份量足
4. **macOS / 模型 / 影片**（候選 1, 19, 23, 24, 25, 28）= 6 個 → 個別獨立沒明顯 series
5. **brainstorm / 反問工具**（候選 31）= 1 個但份量大 → deep blog 適合

### 寫作優先序建議
1. **先寫 quick wins 1-3 篇暖身**：候選 #1（5 個 concurrent 衰減 91%）或 #5（vector DB retire）這兩個都是「有量化數據 + 第一人稱故事 + 完整 retrospective」三條件都到
2. **建立 blog identity**：候選 #2（rules 載入機制）跟 #4（25KB cap 三類解法）這類「官方文件沒寫清楚的內部機制」可以是定位的 anchor
3. **不要先寫 deep blog**：candidate #31 / #32 / #34 都需要重新組織思路，初期不適合扛壓力
4. **可拆 series**：「為什麼我評估完不採用 X」可以做成至少 6 篇 series（candidate #10, 11, 13, 14, 29, 30）

### 跟既有 wiki cluster 的 gap
- **題材 gap**：wiki 沒有「我評估了 N 個工具最後選了 Z」這種 narrative 型 entry — A 候選裡的工具評估類正好補這個 gap
- **個人 lens gap**：wiki 多是 `lifecycle: verified` 的事實型，blog 要的「個人故事 + 第一人稱 + 為什麼這樣選」沒地方放 — blog 等於是 wiki 的 narrative companion

### 風險
1. **時效性**：候選 #6（CC 第三方 endpoint 5 個 regression）/ #21（caching 8 廠對比）/ #28（本地推理死路）這類 snapshot blog 半年內可能過時 → 寫 timestamp + stale-by 註記
2. **公司 context 滲透**：候選 #16（multi-account quota）/ #20（chrome extension）細節已 sanitize 過進 wiki，blog 寫的時候要再確認沒 leak
3. **吃 CC 主題天花板**：36 個候選有 25+ 跟 CC 強相關 → 如果想擴充 audience 廣度，剩下的 macOS / 影片 / 模型題材可以平衡
4. **「不採用 X」系列風險**：candidate #10 / #11 / #13 涉及具體第三方工具（PullMD / claude-context / context-mode / codegraph / react-doctor 等）負面評價 → 需要小心 phrasing（聚焦「在我的 stack 不採用」不是「工具爛」）

### Surprise observation
1. **量化證據密度高**：候選裡很多有具體數字（5/6 grep vs vector / 1739 sessions 0.4% / 1206 sessions 23/23 / 90 分鐘掉 66% / 430ms → 130ms / 12% 級距），這在「個人技術 blog」題材裡是稀有的——可作為 blog identity 差異化
2. **失敗 / 退役 / 否決的紀錄密度極高**：~30% 的 entry 都是「試了 → 不採用」的負面結果，這是個人 blog 罕見資產（多數 blog 偏 success story / how-to）→ 可建立「failure-as-content」品牌
3. **多 source 跨檔 entry 不少**：候選 #18（wiki + memory 系統設計）/ #32（memory→wiki 雙系統）/ #34（vendor bridge framework）都需要從 5+ files 重組——這類 deep blog 是 wiki 沒法替代的角色
4. **Wiki promotion 的 deduplication**：好幾個 wiki entry（如 `cc-vendor-bridge-toolkit`, `cn-model-swap-landscape`, `adversarial-brainstorm-toolkit`, `design-image-gen-routes-toolkit`）是從 memory cluster promote 上來的——這些已 distill 過所以最適合直接 blog 化（quick win）
