# Voice Profile — CC Dialogue Register (v2)

## Caveat（必讀）

**這份 profile 是 register catalog，不是 blog writing template。**

CC dialogue 是「對 AI 工具說的話」，和 blog 的「對人類讀者寫的文章」在本質上不同。搬移前必須理解三個根本差異：

1. **CC 是即時協作，blog 是成文論述**。CC 訊息中位數 40 字，11.9%（779 條）的訊息不超過 30 字（「commit」「繼續」「先試試看」「都可以做」），這是在跑工作流程，不是在寫作——把「好，繼續」搬進 blog 等於把 terminal session 截圖貼上去

2. **CC 對象是 AI，沒有讀者**。CC 裡大量出現的「你確定」（10 次）「你搞錯了」「你誤會了」是糾正 AI，不是對話體；「1.ok 2.ok 3.看你」是指令回饋，不是論述；這兩種模式搬進 blog 都會讓讀者困惑「他在跟誰說話？」

3. **CC 包含大量工作脈絡殘留**（比如貼進對話的 skill 模板、session 格式文件、API 回傳值）——這些已被過濾，但即便是乾淨語料，CC 的思考仍然是「邊做邊想」碎片流，blog 是「想完再寫」

**正確用法**：寫 blog 想確認某個語感是否真實時，查 CC 語料有沒有對應證據。特別適合驗證「技術判斷語式」「取捨說明邏輯」「第一人稱位置」這三類。**不要**把 CC 的指令語氣、即時自我修正碎片、編號回應（1/2/3）直接搬進 blog。

## v1 → v2 主要差異（污染清除後）

| 指標 | v1（含污染）| v2（乾淨）| 變化 |

## Register 切分

CC 對話內部有四個 sub-register，語氣差很大。

### Sub-register A：精簡指令（高頻）

**規模**：779 條短於 30 字（11.9%）；30-50 字另有 940 條（14.4%）。合計精簡指令約佔 26%

**特徵**：
- 動詞起手，省略主詞（「commit」「繼續」「先試試看」「照順序來吧」）
- 每個字有作用，省略贅字到極限
- 常是對上一輪 AI 回應的確認 / 推進（「好，繼續」「都可以做」「可以，你就自主進行吧」）
- 出現「先 X，然後 Y」的兩步指令串（「先把今天的重新跑看看」「先這樣，之後再說」）

**代表例**：
```
commit
繼續
先處理記憶和wiki
都可以做
照順序來吧
ok，直接做到底
好，先這樣吧，結案
先走A吧
好，發布
你試試看
```

**blog 套法**：**完全不適用**。這個 sub-register 是工作流程語言，不是論述語言。

---

### Sub-register B：編號回應（低頻但明顯）

**規模**：含數字 1. 開頭的訊息估約 873 條，但多數混入長訊息（純編號回應約佔 2-3%）

**特徵**：
- AI 問了 N 個問題，使用者逐一回答（「1.ok 2.可以 3.看你決定」）
- 節省解釋，直接定案
- 有時帶補充說明（「1.ok 2.可以，但要記得 X」）

**代表例**：
```
1.不用review，直接推上去吧，那個repo本來就是備份作用
2.GGGODLIN/claude-config是private吧？
3.算了，不能備份就不能備份吧
```
```
1.能公開就公開，興趣公開應該還好
2.可以，需要我填資料的時候通知我就好
3.1吧，先全部試試看，還有我想到有可能是我有開VPN
```

**blog 套法**：不直接用，但「逐項回應」的心智模式可以轉化為 blog 的「逐條釐清」結構

---

### Sub-register C：探索提問（高頻）

**規模**：含問號的訊息約 1,575 條（24.1%）

**特徵**：
- 不確定答案，真的在問（不是反問 AI）
- 常帶「有沒有辦法」（102 次）「能不能」（77 次）「有沒有」（270 次）「還是」（373 次）
- 「還是」頻繁出現用作分支探索（「走 A 還是 B？」「靠第三方 API 還是自己爬？」）
- 「比較好」（42 次）多用於詢問技術路線選擇

**代表例**：
```
內文預覽150字是某種硬條件限制，還是純粹我腳本這樣寫？
派subagent時有辦法指定模型嗎？甚至思考強度呢？
有原生的追熱門為何不用？
做extension應該只是抓登入資訊給其他現成的服務用吧？還是我要自己爬也可以？
看起來長期使用的話會因為這個memory hook導致污染我的記憶對吧，這有辦法處理嗎？
```

**blog 套法**：Sub-register C 最接近 blog——問句形式可以保留，但要轉成「我當初的疑問是」或自問自答模板，不是跟 AI 發問的語氣

---

### Sub-register D：展開討論（思考密度最高，乾淨版比例大幅提升）

**規模**：1,551 條字數超過 200 字（23.7%）；字數 50-200 字 3,282 條（50.1%）

**特徵**：
- 說明需求的完整邏輯（「我想要的是 X，因為 Y，但擔心 Z」）
- 說明技術判斷（比較 A vs B，說明為何不選 C）
- 自我修正在同一則訊息裡發生（先提一個方向，後半段修正）
- 帶有「反正」（55 次）收尾，表示接受某種妥協
- 「另外」（104 次）頻繁出現，做話題跳轉補充

**代表例**：
```
應該這樣說，資料撈取失敗分兩個層面，一個是retry有機會，一種是必須要我處理的
（比如說vpn）。可retry的就在retry幾次後才放棄，最後彙整成issue備註，讓我
要求你分析的時候先處理補資料
```
```
一開始就是想走方案A，比起快速主要是想把流程固定下來，因為我不會每次改了A，
就把BCDE等等各種情境都測一遍，但是自動化可以慢慢在背景跑
```
```
其實也不用自動化，完全可以我想要看報告的時後你當下fetch就好。畢竟現在分析
也沒有做自動化，我也是要記得叫你分析，對我來說gap是一樣的，放到github沒有
比較省，唯一的好處就是能保證每天產資料而已
```

**blog 套法**：這個 sub-register 最接近 blog 的段落邏輯，尤其取捨說明的「雖然 X，但 Y，選 Y 因為 Z」結構可以直接對應 blog 的論述段

## 句型 patterns

### A. 取捨陳述模式（最有 blog 價值，CC 獨有密度）

CC 語料裡頻繁出現「A vs B + 選 X 因為 Y + 不選 Z 因為 W」的技術取捨邏輯，這是所有 register 裡最接近 blog 技術論述的句型，也是 CC register 最獨特的貢獻——threads 有「省流排序」，LINE 有「一句斷論」，但 CC 才有完整的**決策說明過程**。

**結構模板**：`[起始假設 X] → [但現實是 Y] → [唯一的好處 / 主要的問題是 Z] → [所以選 W]`

**原文範例**：
```
其實也不用自動化，完全可以我想要看報告的時後你當下fetch就好。畢竟現在分析
也沒有做自動化，我也是要記得叫你分析，對我來說gap是一樣的，放到github沒有
比較省，唯一的好處就是能保證每天產資料而已
```
```
一開始就是想走方案A，比起快速主要是想把流程固定下來，因為我不會每次改了A，
就把BCDE等等各種情境都測一遍，但是自動化可以慢慢在背景跑
```
```
感覺keyword比較穩，但各種方案都可以記錄下來，初期可以都做，比較怎麼做效果好
```
```
主要是想把opus review和codex review綜合起來比較，並寫成繁體中文的md讓我review
這個流程記錄下來
```

**blog 套法**：Sub-register D 的取捨邏輯放大成 blog 段落。原本一句話（「放到 github 沒有比較省，唯一的好處是保證每天產資料」），展開成三段：「初始假設是 X → 實際上 Y → 所以選 Z 的真正理由是 W」。這是 CC 對 blog 最有價值的輸出。

---

### B. 精簡疑問 + 順帶補充（高頻）

**模板**：`主問題（一句）+ 分支條件（一句）+ 備案（一句）`

**原文範例**：
```
有沒有更清楚的名字？
daily-radar的話有撞名嗎？
daily-topic-radar怎麼樣？
```
```
那如果重整後還是沒回來呢？（主問）
還是去把 cc-paired-context-override.md 改掉？（備案）
```
```
派subagent時有辦法指定模型嗎？你剛剛用的是哪個模型？
甚至思考強度呢？（延伸）
```

**blog 套法**：問句 + 補充 = threads 已驗證的「自問自答」結構。「主問題，然後這樣不行，因為 X，所以換個角度想，有沒有 Y 的可能」

---

### C. 條件限縮指令（CC 特有，blog 不適用）

**模板**：`動詞 + [限制條件] + [原因]`

**原文範例**：
```
這是個vibe coding專案，所以git由你來操作（授權 + 條件）
不用review，直接推上去吧，那個repo本來就是備份作用（否定 + 原因）
跟這個session無關的code不要動，因為我是測好才開始這個對話（限制範圍 + 原因）
```

**blog 套法**：**不適用**。帶限制的指令語感是 CC 工作協作語言，博文裡沒有操作對象

---

### D. 二元探索句（CC 特有，可部分轉化）

**模板**：`X 還是 Y？（如果 Y，那 Z 呢？）`

**頻率**：「還是」373 次，是 CC 最高頻的探索詞

**原文範例**：
```
內文預覽150字是某種硬條件限制，還是純粹我腳本這樣寫？
做extension應該只是抓登入資訊給其他現成的服務用吧？還是我要自己爬也可以？
看不懂，所以搜尋的部分我這邊有辦法解嗎？還是只能等deepseek修？
```

**blog 套法**：「X 還是 Y」→ blog 可以用「起初我以為要走 X，後來發現其實 Y 更合適，原因是...」轉化為論述。二元探索的心智模式是真實的，但問句語氣要轉成陳述

---

### E. 量化確認（三個 register 共有，CC 密度最高）

**模板**：具體數字 + 直接判斷

**頻率**：含 K/M/%/token/字元等量化的訊息 510 條（7.8%），加上其他數字估計超過 1,500 條

**原文範例**：
```
約157K tokens，可是你不是1M嗎
我現在用掉80%再來壓縮
這邊大概600K-800K是claude發瘋臨界點
25KB硬要達標的話我可能要縮很多敘述
5/13的周用量+50%你沒找到官方文章背書嗎？
```

**blog 套法**：核心 marker，直接帶進 blog（和 threads、LINE 三者一致，見跨 register 穩定 DNA 段）

## 自我修正的語言特徵（CC 獨有、CC 最高密度）

CC 語料最突出的獨特特徵：**即時自我修正密度遠高於其他 register**。使用者在對 AI 說話時，思路展開的同時就已經在自我糾錯。「等一下」（66 次）「不對」（32 次）「應該說」（18 次）「忽然想到」（24 次）是 CC 語料的四大自我修正 marker，這四個詞在 threads 和 LINE 都低頻，是 CC-exclusive 的思維呈現。

**類型一：段落內修正**（同一則訊息先提後修）
```
應該這樣說，資料撈取失敗分兩個層面，一個是retry有機會，一種是必須要我處理的
（先說「失敗」→ 修正成「兩種失敗模式」）
```

**類型二：跨訊息修正**（下一則推翻上一則）
```
不對，我發現這個檔案一直在變大，應該還在寫入，我們等一下看看
不對，我不認為這要加到 global 的
```

**類型三：即時中斷**（想到問題就打斷 AI）
```
等一下，我發現兩次產的截圖文字還會不一樣，目前這些描述都是臨時產出的嗎
等一下，我其實應該先把這個error重現，再開始修才知道有沒有修好
等一下，我誤會了，這個名單是by repo的嗎？不是整個github乃至整個世界都共用的嗎
```

**類型四：記憶修正**（修正 AI 記憶錯誤）
```
你搞錯了，我是要cmux這邊可以直接打開claude
你確定？我記得之前測起來不是這樣
你的結論不對，我在那個session後面還有更嚴謹的討論
```

**blog 套法**：CC 的自我修正是即時對話殘留，不適合直接搬。但「先提一個假設，再自己推翻」的思維模式可以轉化成 blog 的「起初我以為 X，但後來...」結構——前提是這個修正必須是 blog 草稿設計時就有機存在的，不能事後強行插入。

## 跨 register 穩定 voice DNA

CC ∩ threads ∩ LINE 三邊都出現的 marker，是真正的 voice 核心，驗證後直接放心進 blog。

| Marker | CC 頻率 | threads 驗證 | LINE 頻率 | blog 信心度 |
|---|---|---|---|---|
| **量化偏好**（具體數字取代「很多/不少」）| 510 條含量化詞（7.8%）；全語料量化密集 | main 必帶具體數字（金額 / 比例 / 時間錨）| 「400K / 600-700K / 15000 字元 / 99 鎂」高頻 | 最強 DNA |
| **擬人化模型動詞** | 「claude 整天到晚掛掉」「opus 發瘋臨界點」「降智」（降智 + 發瘋 + 爆炸 = 8 次）| main 標誌（「降智」「爆衝」「跑偏」「找不到就業機會」）| 「opus 開始準備發瘋」「gemini 大便」「antigravity 噴錯」| 最強 DNA |
| **這邊**（第一人稱位置詞）| 70 次（「我這邊有辦法解嗎」「你這邊」「這邊大概」）| main 81 次核心 marker（「這邊自問自答」「這邊推薦」）| 83 次 | 核心 DNA |
| **先 X 再/然後 Y**（時序排列）| 「先」581 次（最高頻詞之一）；「先 X 然後 Y」102 次 | main 段落推進用 | 「先 A 再 B」結構高頻 | 核心 DNA |
| **量化 vibe 判斷**（爛/沒用/過度）| 「爛咖」「降智」「過氣」類 7 次（低）；「感覺」110 次帶評斷 | 「爛咖」「就這」「降智」reply 高頻 | 「爛」143 次 | 可進 blog |
| **vibe**（動詞化）| 15 次（「vibe coding 專案」「vibe 了一個」）| main 「就趁連假 vibe 了一個 X」 | 「vibe 一個 / vibe 健身」| 核心 DNA |
| **反正**（接受妥協收尾）| 55 次（「反正我都會叫你做」「反正紀錄盡量完善」）| 段尾偶見（「選自己喜歡的就好」）| 「反正就這樣吧」多次 | 可進 blog |
| **另外**（補充話題跳轉）| 104 次（CC 最高頻的跳轉詞）| main 段落補充偶見 | LINE 技術 register 常見 | 偶用 OK |

**最重要發現**：「量化偏好」和「擬人化模型」是三個 register 都高頻、CC 裡也密集的 DNA，這代表這兩個特徵是最強的 voice fingerprint，blog 只要缺了這兩個就不像本人。「這邊」作為第一人稱位置詞在三邊皆高頻，也是 blog 的安全 marker。

## Anti-pattern（CC 裡最容易翻車的搬移）

| 從 CC 搬 | 為什麼翻車 | 修法 |
|---|---|---|
| 「等一下，我發現一個問題，如果...」 | blog 不是即時反應，讀者不知道在「等」什麼 | 改「這裡有一個值得注意的問題：」 |
| 「你確定這樣做沒問題嗎？」 | 對象是 AI，blog 讀者不是 AI | 改「這裡要確認一個細節：」 |
| 「算了，先這樣，之後再說」 | CC 工作流程隨機終止語，blog 要有明確收尾 | 改「目前先做到這一步，後續討論 X」 |
| 「好，繼續」（段落推進）| blog 的段落推進靠邏輯連接詞，不是工作流程推進指令 | 改「接著看下一個問題」 |
| 「應該說，我其實是想要 X」 | blog 不應讓讀者看到「未完成的思路」 | 在草稿階段就直接寫清楚 X |
| 「1.ok 2.可以 3.看你」 | 對象是 AI 的問題，blog 讀者不是在等你回覆選項 | 改成「分三點說明：第一...第二...第三...」 |
| 「反正我都會叫你做」「交給你判斷」 | 委派語氣，對象是 AI | 完全拿掉；blog 沒有待命的 AI |
| 「算了，那沒事了」 | CC 工作流程打斷收尾 | blog 段落不能這樣收；要寫結論 |
| 即時數字確認（「157K tokens，可是你不是 1M 嗎」）| 疑問語氣 + 對話殘留 | 轉化為陳述「我以為 context 是 1M，但實際吃到 157K 就壓縮了」 |
| 「幫我 + 動詞」（454 次）| blog 讀者不是工具，「幫我」的語氣不對 | 完全拿掉或改成「接著要做的是 X」 |
| 「看你」「你決定」 | 委派給 AI | 完全拿掉，blog 論述不委派讀者 |

## 給 blog 寫作的具體 takeaway

1. **Sub-register D（展開討論，23.7%）是 blog 的最佳語料來源**。乾淨語料中字數超過 200 字的訊息遠多於污染版估計（1,551 條 vs 舊版估 419 條），代表使用者本人的長篇技術推理在 CC 裡其實很豐富，直接拿來當 blog 段落的邏輯骨幹，補連接詞、提高精煉度即可

2. **取捨陳述邏輯是 CC register 最有 blog 價值的句型**。「A 不選的原因是 X，選 B 是因為 Y，但 Y 也有一個代價是 Z」——這種三段式決策邏輯在 CC 裡是日常（「放到 github 沒有比較省，唯一的好處就是能保證每天產資料」），在 blog 裡是技術論述的核心，兩邊完美接軌

3. **自我修正模式轉化而非直接移植**。CC 的「等一下」「應該說」「不對」（合計 116 次）都是即時對話殘留，不能原文搬。但「先提假設 → 再自我推翻」的思路結構可以在 blog 設計階段有機種入，這是 CC 給 blog 的最獨特思維模式貢獻

4. **跨三個 register 都高頻的 DNA（量化 / 擬人化 / 這邊）是最安全的 blog anchor**。當你不確定某個表達是不是真實 voice，拿這三個當校準基準點。量化（510 條含量化詞）+ 擬人化（8 次明確擬人化詞，全語料密集）+ 這邊（70 次）三者一致出現 = 最強 fingerprint

5. **CC marker 是 validation 用，不是 injection 用**。看到 CC 某個表達高頻，不代表 blog 要補這個表達；只能用來確認「我 blog 自然寫出來的 X 跟 CC 語料對得上 → 這是真實 voice，不是被 AI 腔污染的」。與 LINE 蒸餾得到的相同硬通則：marker 是驗證工具，不是注入素材。「等一下我想到了」在 CC 66 次高頻，但在 blog 依然不適用，因為這是 CC-exclusive 的即時反應語境

## Pending（蒸不出來的軸）

1. **「寫給讀者的技術論述」這軸在 CC 語料裡幾乎不存在**。CC 語料是說話語言（協作 / 指令 / 即時討論），不是寫作語言，無法從中蒸出「如何為公開讀者解釋技術概念」的 voice。這個軸還是要靠 threads 17 main 篇當主要參照

2. **Lead 開場在 CC 無意義**。CC 開場要不是「今天的分析」這種 token，要不是背景情境鋪陳，沒有「對讀者的第一句話」這種結構。Blog lead 的校準繼續用 threads voice profile

3. **篇章收尾在 CC 是 session 結案語**（「好，先這樣，結案」「commit，推上去」），跟 blog 的 takeaway 完全不同結構，無法類推

4. **CC 語料的情緒密度遠低於 LINE**。CC 幾乎沒有髒話（幹 / 爛之類在 CC 偶見但 < 5 次），情緒性詞彙被工作協作語彙取代。這也驗證 CC register 的主基調是「實事求是的技術協作」而非「情緒發洩」
