# Voice Profile — CC Dialogue Register (v1)

## Caveat（必讀）

**這份 profile 是 register catalog，不是 blog writing template。**

CC dialogue 是「對 AI 工具說的話」，和 blog 的「對人類讀者寫的文章」在本質上不同。搬移前必須理解三個根本差異：

1. **CC 是即時協作，blog 是成文論述**。CC 訊息中位數 42 字，21.5%（1,638 條）的訊息不超過 20 字（「commit」「先這樣」「都可以做」「繼續」），這是在跑工作流程，不是在寫作——把「ok，接著做」搬進 blog 等於把 TUI session 截圖貼上去

2. **CC 對象是 AI，沒有讀者**。CC 裡大量出現的「你確定」「你搞錯了」「你誤會了」是糾正 AI，不是對話體；「1.好 2.ok 3.看你」是指令回饋，不是論述；這兩種模式搬進 blog 都會讓 reader 困惑「他在跟誰說話？」

3. **CC 包含大量工作脈絡殘留**（skill prompt / plan / template）這些已被過濾，但即便是乾淨語料，CC 的思考仍然是「邊做邊想」碎片流，blog 是「想完再寫」

**正確用法**：寫 blog 想確認某個語感是否真實時，查 CC 語料有沒有對應證據。特別適合驗證「技術判斷語式」「取捨說明邏輯」「第一人稱位置」這三類。**不要**把 CC 的指令語氣、自我修正碎片、數字回應（1/2/3）直接搬進 blog。

## Register 切分

CC 對話內部有四個清晰的 sub-register，語氣差很大。

### Sub-register A：精簡指令（最高頻）

**規模**：約 2,255 條（29.6%），字數 1-30 字，無問號

**特徵**：
- 動詞起手，省略主詞（「commit」「繼續」「先處理記憶和wiki」「照順序來吧」）
- 省略贅字到極限，每個字有作用
- 常是對上一輪 AI 回應的確認 / 推進（「好，繼續」「都可以做」「可以，你就自主進行吧」）
- 出現「先 X，然後 Y」的兩步指令串（「先把今天的重新跑看看」「先這樣，之後再說」）

**代表例**：
```
commit
繼續
先處理記憶和wiki
都可以做
照順序來吧
ok，直接做到底
好，先這樣吧，結案
```

**blog 套法**：**完全不適用**。這個 sub-register 是工作流程語言，不是論述語言。

---

### Sub-register B：編號回應

**規模**：約 80 條（1.1%，但實際更多，因為混在長訊息裡）

**特徵**：
- AI 問了 N 個問題，使用者逐一回答（「1.ok 2.可以 3.看你決定」）
- 節省解釋，直接定案
- 有時帶補充（「1.ok 2.可以，但要記得 X」）

**代表例**：
```
1.不用review，直接推上去吧
2.GGGODLIN/claude-config是private吧？
3.算了，不能備份就不能備份吧
```

```
1.能公開就公開
2.需要我填資料的時候通知我就好
3.先全部試試看，然後我想到有可能是我有開VPN
```

**blog 套法**：不直接用，但「逐項回應」的心智模式可以轉化為 blog 的「逐條釐清」結構

---

### Sub-register C：探索提問（高頻）

**規模**：約 1,648 條（21.6%）

**特徵**：
- 不確定答案，真的在問（不是反問）
- 常帶「有沒有辦法」「能不能」「有可能」「是不是」（次數：「有辦法」110 / 「對吧」95 / 「還是」427）
- 「還是」頻繁出現用作分支探索（「走A還是B？」「用這個還是那個比較好？」）
- 「比較好」45 次，多用於詢問技術路線選擇

**代表例**：
```
可以先試試groq嗎？不行的話再想別的
有原生的追熱門為何不用？
但這樣是不是要工程師記得這個指令，如果我用自然語言要求你看shopify changelog，會調用這個嗎
hook的話應該不會額外佔用AI的token吧？
```

**blog 套法**：Sub-register C 是最接近 blog 的 register——問句形式可以保留，但要轉成「我當初的疑問是」或自問自答模板，不是跟 AI 發問的語氣

---

### Sub-register D：展開討論（思考密度最高）

**規模**：約 419 條（5.5%），字數 100-600 字

**特徵**：
- 說明需求的完整邏輯（「我想要的是 X，因為 Y，但擔心 Z」）
- 說明技術判斷（比較 A vs B，說明為何不選 C）
- 自我修正在同一則訊息裡發生（先提一個方向，後半段修正）
- 帶有「反正」（59 次）收尾，表示接受某種妥協

**代表例**：
```
其實也不用自動化，完全可以我想要看報告的時後你當下fetch就好。畢竟現在分析也沒有做自動化，我也是要記得叫你分析，對我來說gap是一樣的，放到github沒有比較省，唯一的好處就是能保證每天產資料而已
```
```
一開始就是想走方案A，比起快速主要是想把流程固定下來，因為我不會每次改了A，就把BCDE等等各種情境都測一遍，但是自動化可以慢慢在背景跑
```

**blog 套法**：這個 sub-register 最接近 blog 的段落邏輯，尤其取捨說明的「雖然 X，但 Y，選 Y 因為 Z」結構可以直接對應 blog 的論述段

## Tone / 語氣 markers

| 標籤 | 原文照引例子 | 出現頻率 | blog 套法 |
|---|---|---|---|
| 自我修正開場 | 「**等一下**，我發現一個問題」「**等一下**，如果 process 一直都活著」「**等一下**，為啥你一直交付半成品」 | 等一下 76 次 | **CC 獨有**，blog 轉化為「但這裡有一個問題」「不對，更準確的說法是」 |
| 重新表述 | 「**應該說**，我覺得你可以要求...」「**應該這樣說**，資料撈取失敗分兩個層面」 | 應該說 18 次 | **CC 獨有**，blog 可用「換句話說」「更精確地說」替代 |
| 思路修正 | 「**不對**，我發現這個檔案一直在變大」「**不對**，我不認為這要加到 global」 | 不對 19 次 | **CC 獨有**，blog 可保留「不對」當段落自我反駁（少量） |
| 接受妥協 | 「**算了**，不能備份就不能備份吧」「**算了**，先這樣做吧」 | 算了 36 次 | 偶爾可進 blog 當「放手式收尾」（threads 已驗證「選自己喜歡的就好」） |
| 技術判斷直球 | 「**感覺好蠢，不採用**」「**感覺可以，就這樣吧**」「**這樣就夠了**」 | 感覺 114 次 | 「感覺好蠢」轉化為 blog「這個設計其實沒有必要」；口語程度降一級 |
| 授權委派 | 「**你覺得怎樣對未來的你比較好就那樣做吧**」「**反正我都會叫你做**」「**交給你，你判斷**」 | 反正 59 次 | **CC 獨有**，blog 不委派 AI |
| 確認語氣 | 「**對吧**？」「**你確定**？」「**這樣不會有問題嗎**」 | 對吧 95 次 / 你確定 10 次 | **[AI 對話限定]**，blog 改成「這裡要注意一點」 |
| 帶觸發的話題跳轉 | 「**話說**，我現在 push 跟 pull claude 好像都會跟我說這次改了什麼」「**對了**，可以先在桌面建一個資料夾」 | 話說 24 次 / 對了 19 次 | 偶用 OK（threads 偶見「最近」「對了」類開場） |
| 即時驚覺 | 「**忽然想到**，目前的架構支不支援從副機發 task」「**我想到一件事**，cc 有說 claude -p 準備走 credit」 | 忽然想到 13 次 | blog 可用「寫到這裡突然意識到」模擬，但要有機生成 |

## 句型 patterns

### A. 取捨陳述模式（最有 blog 價值）

CC 語料裡頻繁出現「A vs B + 選 X 因為 Y + 不選 Z 因為 W」的技術取捨邏輯，這是所有 register 裡最接近 blog 技術論述的句型。

**原文範例**：
```
其實也不用自動化，完全可以我想要看報告的時後你當下fetch就好。畢竟現在分析也沒有做自動化，我也是要記得叫你分析，對我來說gap是一樣的，放到github沒有比較省，唯一的好處就是能保證每天產資料而已
```

```
一開始就是想走方案A，比起快速主要是想把流程固定下來，因為我不會每次改了A，就把BCDE等等各種情境都測一遍，但是自動化可以慢慢在背景跑
```

```
感覺keyword比較穩，但各種方案都可以記錄下來，初期可以都做，比較怎麼做效果好
```

**blog 套法**：Sub-register D 的取捨邏輯可以直接放大成 blog 段落。原本一句話（「放到 github 沒有比較省，唯一的好處是保證每天產資料」），展開成三段：「我的初始假設是 X → 實際上 Y → 所以選 Z 的真正理由是 W」

---

### B. 精簡疑問 + 順帶補充（高頻）

**模板**：`主問題（一句）+ 補充條件（一句）`

**原文範例**：
```
有沒有更清楚的名字？（主問題）
daily-radar的話有撞名嗎？（追問）
daily-topic-radar怎麼樣？（提案）
```

```
那這些觸發時機信心度如何？有辦法精準觸發嗎？我有想到另一個時機，就是push的時候檢查，但有點擔心loading會不會很重
```

**blog 套法**：問句 + 補充 = threads 已驗證的「自問自答」結構。「主問題，然後實際上這樣不行，因為 X，所以換個角度想，有沒有 Y 的可能」

---

### C. 條件限縮指令（CC 特有，blog 不適用）

**模板**：`動詞 + [限制條件]`

**原文範例**：
```
這是個vibe coding專案，所以git由你來操作（授權 + 條件）
不用review，直接推上去吧，那個repo本來就是備份作用（否定 + 原因）
跟這個session無關的code不要動，因為我是測好才開始這個對話（限制範圍 + 原因）
```

**blog 套法**：**不適用**。這種帶限制的指令語感（「只做這個不要動那個」）是 CC 工作協作語言，博文裡沒有操作對象

---

### D. 二元探索句（CC 特有，可部分轉化）

**模板**：`X 還是 Y？（如果 Y 的話，那 Z 呢？）`

**原文範例**：
```
分析一定要用腳本嗎？不能用AI讀取所有對話紀錄直接做分析嗎？腳本的話定義是不是會比較嚴格
外部網路深度研究，著重在記憶上限突破25KB
那感覺還是local的做法比較穩，我可以放心換帳號
```

**blog 套法**：「X 還是 Y」→ blog 可以用「起初我以為要走 X，後來發現其實 Y 更合適，原因是...」轉化為論述

---

### E. 數字量化確認（三個 register 共有）

**模板**：具體數字 + 直接判斷

**原文範例**：
```
約 157K tokens，可是你不是1M嗎
我現在用掉80%再來壓縮
這邊大概600K-800K是claude發瘋臨界點
25KB硬要達標的話我可能要縮很多敘述
```

**blog 套法**：核心 marker，直接帶進 blog（這和 threads、LINE 三者一致，見跨 register 穩定 DNA 段）

## 自我修正的語言學特徵（CC 獨有）

CC 語料最突出的 CC-exclusive 特徵是**即時自我修正密度遠高於其他 register**。使用者在對 AI 說話時，思路展開的同時就已經在自我糾錯。

**類型一：段落內修正**（同一則訊息先提後修）
```
應該這樣說，資料撈取失敗分兩個層面，一個是retry有機會，一種是必須要我處理的
（先說「失敗」→ 修正成「兩種失敗」）
```

**類型二：跨訊息修正**（下一則推翻上一則）
```
不對，我發現這個檔案一直在變大，應該還在寫入，我們等一下看看
不對，我不認為這要加到 global 的
```

**類型三：記憶修正**（修正 AI 記憶錯誤）
```
你搞錯了，我是要cmux這邊可以直接打開claude
你確定？我記得之前測起來不是這樣
```

**blog 套法**：CC 的自我修正是即時對話殘留，不適合直接搬。但「先提一個假設，再自己推翻」的思維模式可以有機轉化成 blog 的「起初我以為 X，但後來...」結構——前提是這個修正必須是 blog 草稿設計時就 organically 存在的，不能事後強行插入

## 跨 register 穩定 voice DNA

CC ∩ threads ∩ LINE 三邊都出現的 marker，是真正的 voice 核心，無需再驗證直接放心進 blog。

| Marker | CC 頻率 | threads 驗證 | LINE 驗證 | blog 信心度 |
|---|---|---|---|---|
| **量化偏好**（具體數字取代「很多/不少」）| 全語料密集（200K / 25KB / 80% / 5 個 / 157K tokens）| main 必帶具體數字 | 400K / 600-700K / 15000 字元 | ✅ 核心 DNA |
| **擬人化模型動詞**（「claude 開始發瘋」「opus 開始準備發瘋」）| 中等頻率（「claude 整天到晚掛掉」「發瘋臨界點」）| main 標誌（降智 / 爆衝 / 跑偏）| 「opus 開始準備發瘋」「gemini 大便」| ✅ 核心 DNA |
| **這邊**（第一人稱位置詞）| 75 次（「這邊不確定」「這邊推薦」）| main 81 次核心 marker | LINE 83 次 | ✅ 核心 DNA |
| **先 X，之後 Y**（時序排列）| 先 684 次（最高頻之一）| main 段落推進用 | LINE 「先 A 再 B」 | ✅ 核心 DNA |
| **爛 / 沒必要 / 過度工程化**（技術評斷直球）| 「感覺好蠢，不採用」「過度工程化」| 「爛咖」「就這」「降智」| 「爛 143 次」 | ✅ 核心 DNA |
| **vibe**（動詞化）| 語料有（「vibe coding 專案」）| main 「就趁連假 vibe 了一個 X」| LINE vibe 一個 / vibe 健身 | ✅ 核心 DNA |
| **反正**（接受妥協收尾）| 59 次（「反正我都會叫你做」「反正紀錄盡量完善」）| 段尾偶見（「選自己喜歡的就好」）| 「反正就這樣吧」 | ✅ 可進 blog |
| **啊 / 吧 / 喔**（語助詞）| 散見（「好吧」「對吧」「算了吧」）| main reply 用 | LINE 啦 244 / 喔 333 | ✅ 偶用 OK |

**最重要發現**：「量化偏好」和「擬人化模型」是三個 register 都高頻、CC 裡也密集的 DNA，這代表這兩個特徵是最強的 voice fingerprint，blog 只要缺了這兩個就不像本人。

## CC-exclusive markers（不能進 blog）

這些是 CC dialogue 才會出現的語言特徵，搬進 blog 會讓讀者困惑或感覺奇怪：

| Marker | CC 用途 | 為什麼不能進 blog |
|---|---|---|
| 「好，繼續」「繼續做」 | 推進 AI 執行下一步 | blog 沒有待命的 AI，沒有「繼續」的對象 |
| 「你確定」「你搞錯了」「你誤會了」 | 糾正 AI 輸出 | blog 沒有 AI 對話對象，搬進去像在跟空氣說話 |
| 「1.ok 2.ok 3.看你」 | 對 AI 的複選題回覆 | blog 不是問卷 |
| 「等一下，我發現...」（即時） | 想到問題中斷 AI | blog 寫完再發，不存在即時中斷；轉化為「這裡有個值得注意的問題」 |
| 「你來做」「交給你判斷」「反正你決定」 | 授權委派 AI | blog 不委派讀者做事（除非是 CTA） |
| 「算了，那沒事了」 | CC 工作流程打斷收尾 | blog 段落不能這樣收 |
| 「先這樣吧，結案」 | 工作 session 收尾 | blog 有正式結尾，不是「結案」 |
| 「幫我 + 動詞」（大量） | 發指令給 AI（幫我 485 次） | blog 讀者不是工具，「幫我」的語氣不對 |
| 純英文指令詞（「commit」「push」「config」）| CLI 工作流程 | blog 要有完整中文句子，光一個英文指令詞沒有論述 |

## Anti-pattern（這些搬進 blog 最容易翻車）

| 從 CC 搬 | 為什麼翻車 | 修法 |
|---|---|---|
| 「等一下，我發現一個問題，如果...」（即時中斷型）| blog 不是即時反應，這種語氣讓讀者以為在 live chat | 改「這裡有一個值得注意的問題：」 |
| 「你確定這樣做沒問題嗎？」 | 對象是 AI，blog 沒有 AI 在那邊被問 | 改「這裡要確認一個細節：」 |
| 「算了，先這樣，之後再說」 | CC 工作流程隨機終止語，blog 要有明確收尾 | 改「目前先做到這一步，後續討論 X」 |
| 「好，繼續」（段落推進）| blog 的段落推進靠邏輯連接詞，不是工作流程推進指令 | 改「接著看下一個問題」「再往下一層」 |
| 「應該說，我其實是想要 X」（重新表述）| CC 裡重新表述很自然，但 blog 不應該讓讀者看到「未完成的思路」 | 在 draft 階段就直接寫清楚 X，不要留「重新表述」的痕跡 |
| 「1.ok 2.可以 3.看你」（編號回應）| 對象是 AI 的問題，blog 讀者不是在等你回覆他的選項 | 如果要逐項，改成「分三點說明：第一...第二...第三...」 |
| 「這個 vibe coding 專案」（CC 工作脈絡）| blog 讀者不知道這個 session 的背景，語境缺失 | 先交代「這是我用 vibe coding 方式做的一個 X 專案」 |
| 即時數字確認（「157K tokens，可是你不是 1M 嗎」）| 疑問語氣，對話殘留 | 轉化為陳述（「我以為 context 是 1M，但實際吃到 157K 就壓縮了」）|

## 給 blog 寫作的具體 takeaway

1. **Sub-register D（展開討論）是 blog 的最佳語料來源**。CC 裡字數超過 100 字、帶取捨邏輯的訊息（約 419 條），直接拿來當 blog 段落的邏輯骨幹，補連接詞、提高精煉度即可

2. **取捨陳述邏輯是 CC register 最有 blog 價值的句型**。「A 不選的原因是 X，選 B 是因為 Y，但 Y 也有一個代價是 Z」——這種三段式決策邏輯在 CC 裡是日常，在 blog 裡是技術論述的核心，兩邊完美接軌

3. **自我修正模式轉化而非直接移植**。CC 的「等一下」「應該說」「不對」都是即時對話殘留，不能原文搬。但「先提假設 → 再自我推翻」的思路結構可以在 blog 設計階段有機種入

4. **跨三個 register 都高頻的 DNA（量化 / 擬人化 / 這邊）是最安全的 blog anchor**。當你不確定某個表達是不是真實 voice，拿這三個當校準基準點

5. **CC marker 是 validation 用不是 injection 用**。看到 CC 某個表達很高頻，不代表 blog 要補這個表達；只能用來確認「我 blog 自然寫出來的 X 跟 CC 語料對得上 → 這是真實 voice 不是被 AI 或 GPT 腔污染的」。與 LINE 蒸餾得到的相同硬通則：marker 是驗證工具，不是注入素材

## Pending（蒸不出來的軸）

1. **「寫給讀者的技術論述」這軸在 CC 語料裡幾乎不存在**。CC 語料是說話語言（協作 / 指令 / 即時討論），不是寫作語言，無法從中蒸出「如何為公開讀者解釋技術概念」的 voice。這個軸還是要靠 threads 17 main 篇當主要參照

2. **Lead 開場在 CC 無意義**。CC 開場要不是「今天的分析」這種 token，要不是背景情境鋪陳，沒有「對讀者的第一句話」這種結構。Blog lead 的校準繼續用 threads voice profile

3. **篇章收尾在 CC 是 session 結案語**（「好，先這樣，結案」「commit，推上去」），跟 blog 的 takeaway 完全不同結構，無法類推
