## 3. 句型模式

### 3.1 長文主文模板

全 33 則主文中有 7 則超過 7 行（#1 / #2 / #11 / #12 / #22 / #27 / #29），這 7 則共用同一套骨架：

```
[1] 時間錨 ＋ 行動宣告（一行）
    「最近把中國各大頂尖模型弄進claude code cli跑差不多一週了，來評價一下」（#12）
[2] 立刻給結論／排序／省流（一行，不留懸念）
    「省流:deepseek V4 pro>>GLM 5.1>=Kimi 2.6>mimo>MiniMax 2.7」（#12）
    「懶人包：codex操作真實瀏覽器的e2e testing場景…消耗少了87.90%、時間少24.56%」（#30）
[3] 編號分項，每項固定四段：能力定位 → 具體數字 → 缺點 → 適用場景
    「1.ds V4 pro:能力相當於opus4.7推出前一晚的opus 4.6 medium effort…
     缺點：思考深度不足，不愛反問人類…
     適合使用場景：深度研究，按照既有skill做事，多輪任務」（#12）
[4] 反面欄位必定存在，而且會明講切換點
    「好話說在前頭:…好話說盡了，以下是抱怨」（#22）
[5] 收尾三選一：疊甲 ／ 自嘲 emoji ／ 下一步宣告
    疊甲：「當然最後慣例疊甲，此設計目前僅在我的環境跑通」（#30）
    下一步：「btw,compact hook做好了，目前正在觀察效果如何」（#24）
```

**關鍵：第 [4] 段是硬性的。** 7 則長文沒有一則只講好或只講壞。主文 #12（中國模型評比）每一項
都有「缺點：」；#22（gpt5.6sol）明寫「好話說盡了」當分界線；#28（Opus5）先滿意再列問題；
#29 先批評再「疊個甲」承認比 Opus4.x 進步。

### 8.2 ⚠️ 最重要的證據邊界：長度上限是平台限制

  部落格文章他會怎麼分節」。

  （#12 五個模型、#22 三優兩缺、#27 五點摘要）時才拆編號。
- 空行分段：長文用空行切「結論／分項／收尾」三塊（#6 / #11 / #12 / #22 / #29 皆是）。

### 8.4 ⚠️ 無法由語料回答的問題（標為無證據，不推測）

- **markdown 小標**：threads 不支援標題層級，33 則主文 0 個小標。這是**平台限制**，
  **不是文體選擇**，不得推論成「部落格文章也不該分節」。
- **引言區塊（blockquote）**：同上，平台不支援，0 使用。不得推論成他排斥這個元素。
- **程式碼區塊**：同上，0 使用。無證據。
- **粗體／斜體強調**：threads 不支援，0 使用。他在 threads 的「強調」手段是換行獨立成句
  （#18「模型能力很強，但智譜很爛」自成一行）。部落格是否該用粗體 — 無證據。
- **2,000 字以上長文的分節邏輯**：語料上限 499 字，無證據。

### 8.5 Blog 版適配：小標規則（補入的 blog 產線規則）

以下不是 Threads 語料結論，而是既有 blog 產線已驗證的適配規則。來源是 v3 的「分段與小標」規則（PR-031）、穩定 voice profile 的 blog anti-pattern 與跨文章校稿紀錄。Threads 沒有標題層級，不能因此取消 blog 的分節。

- blog 版必須使用 `##` 小標分段；不能整篇只有空行或 `---`。
- 開場 lead 直接進鉤子，不加小標；小標從第二段開始。
- 一篇約 5–8 個小標，對應文章 beat，不把每個段落都拆成教學步驟。
- 小標使用陳述式、口語式寫法，像自然分段，不使用「處置」「結論」「總結」等公文標題。
- 避免疑問句小標對讀者建立教學框架；自問自答型疑問小標只有在正文緊接著回答時才可用。

### 12.1 Blog 產線跨文章硬閘（補入）

以下規則不是 V5 Threads 語料的新結論，而是既有 blog 產線跨文章驗證後補入的硬閘。來源是 v3 的 Anti-pattern、穩定 voice profile 與跨文章校稿紀錄。它們負責防止寫手把模型常見的文章形狀帶進 blog。

- **禁止「不是 X，是 Y」工整對偶**：判斷直接講，對比靠內容與語氣，不靠重複句骨架。
- **破折號每篇最多 1–2 個，預設不用**：優先用句號、冒號、逗號或括號；標題不用破折號。
- **禁止日期牆**：素材的逐日時間戳不直接搬進文章；只有日期本身會改變讀者判斷時才保留人類可讀日期。
- **禁止替自己的段落打分**：不寫「這一段是核心」「本篇最重要」等自我加冕句，讓內容自己成立。
- **禁止蒸餾自創複合標籤或抽象擬人詞**：如「被動硬牆」一類讀者無法從行為理解的詞，改寫成白話描述。
- **禁止收尾複述全文**：結尾落在最後一個具體事實、真實態度或下一步，不把前文換句話重講。
- **禁止假洞見鉤子**：不先說「這裡有個反直覺的點」，直接寫出數字、對照或轉折。
- **維持外部讀者距離**：內部代號、檔名、路徑、步驟編號與未約定俗成的技術黑話要白話化或刪除。
- **控制負面框架**：失敗與否決可以保留，但文章落點放在讀者帶走什麼，不讓全文卡在「沒贏」或「不值得」。

**⚠️ 不列為 anti-pattern 的三件事（證據不足，標為無規則）**：markdown 小標、引言區塊、
粗體強調。Threads 不支援這些元素，不代表 blog 禁止它們；blog 小標規則見 §8.5。

## 16. 計算口徑附錄

所有數字的產生方式。任何一條都可以用同樣口徑重跑。

### 16.1 語料切分

- **threads 兩檔**：以正規表示式 `\n## #(\d+)\n` 切則。每則剝除 `**YYYY-MM-DD HH:MM**`
  時間戳行與 `<https://…>` 網址行，再剝除首尾的 `-` 與空白。切出主文 33 則、回覆 1,147 則，
  與檔頭宣告的數量一致。
- **LINE**：每行一則訊息。以 `^\d{4}\.\d{2}\.\d{2} \d{2}:\d{2} \S+ (.*)$` 剝除日期、時間、
  暱稱，取剩餘內容。抽樣 602 行全部非空。
- **CC**：以單獨一行 `---` 分隔訊息。452 行切出 154 則。

### 16.2 字數

字元數 ＝ Python `len()`，**含**全形／半形標點與行內空白，**不含**已剝除的時間戳與網址行，
**含**換行字元。因此「平均 181.9 字」是含標點的字元數，不是中文字數。

### 16.3 Emoji 計數

正規表示式字元類 `[\U0001F300-\U0001FAFF☀-➿⬀-⯿]`，逐字元計數。

- 已知限制：`☺️` 會被計為 1 個基底字元 `☺`（變體選擇符 U+FE0F 不計），因此表中寫 `☺`。
- 已知限制：`✋😭🤚` 這類組合序列按單字元拆開計數（回覆 #569）。
- 顏文字（QQ / XD / 😇 以外的純 ASCII 表情）**不計入** emoji 統計。「QQ」另見主文 #22 / #32。

### 16.4 關鍵詞計數的兩種口徑（本檔混用，逐處已標示）

1. **則數／出現次數**（Python）：`sum(1 for item if w in item)` ＝ 含該詞的**則數**；
   `sum(item.count(w))` ＝ **總出現次數**。§3.2、§6、§9 的數字採此口徑。
2. **grep 命中行數**（`grep -c`）：計的是**行**不是則，一則多行會重複計。§4.3 的「屌打 6」
   「脆 8」等採此口徑，已在表頭標明「grep 行數」。兩種口徑不可互相加總。

### 16.5 期間切法

`2024-01-01..2024-12-31`／`2025-01-01..2025-12-31`／`2026-01-01..2026-03-31`／
`2026-04-01..2026-06-30`／`2026-07-01..2026-12-31`，以每則的日期字串做字典序比較。
最後一段實際只到 2026-08-18（主文）／2026-08-18（回覆），故稱「2026 Q3（7/1–8/18）」。
