模型分工：不必每件事都用最強模型

額度用完之後，除了換模型，還能重新安排工作。

你很習慣把工作交給 Fable。某天它不能用了，其他模型還能用。
你會直接換一顆繼續，還是調整誰負責哪一段？

「用完了」不是同一件事

狀況一
Fable 專屬上限到了，方案的共享用量還有剩。官方列出的處理方式之一是改用其他模型。今天講的方法對這一種有幫助。
狀況二
共享 session／週用量上限到了。切模型不能恢復額度。

條件查證日 2026-09-09。不同方案的 Fable 限制不同，不要套到所有帳號。

02本場帶走什麼

三種做法，前兩種並列

orchestrator
把工作交出去
主模型拆解與協調，subagent 承接有邊界的工作。我日常最常用的一種。
advisor
把判斷借進來
執行中的模型繼續做事，需要另一個判斷時才請顧問。
effort
同一顆，不同投入
同一模型也能調整推理投入，不只在模型之間切換。

orchestrator 與 advisor 是並列選項，不是新舊替代。「最常用」是我的使用經驗，不是統計。全場用靜態歷史案例與設定示例，不現場操作，也不承諾省幾成。

03先分清楚

把工作交出去，還是把判斷借進來

差別在交出去的是什麼。派工交出的是一件有範圍、有驗收條件的工作，review 或檢查也算一件工作；顧問借的是對 main 自己某個判斷的第二意見，沒有交付物，只有意見。責任都還在你。

做法主流程保留什麼交出去什麼這場的案例
orchestrator任務脈絡、分派、整合與驗收責任一段可界定的實作、review 或檢查資料遷移的 subagent-driven 實作階段
advisor原本工作的執行與後續決策某一次判斷或另一個視角顧問指出提問方式的盲點

三個詞

main
目前對話中負責協調的模型。
subagent
被委派去做一段工作的 agent。不是每個 subagent 都在寫程式。
advisor
被要求提供判斷的角色，不等於自動取得後續修改權。

一個常見誤解：「Fable 當主管、便宜模型當工人」。主模型可以不同，角色不等於能力排名。等一下的案例是 Fable 帶 Opus，那是那一天的配置，不是規則。

兩張圖出自 Anthropic 官方說明（ClaudeDevs thread），圖中的 Fable 5 與 Sonnet 5 是官方示例配置，不是規則——哪個角色配哪個型號由你決定。

04orchestrator

派工時到底在選什麼

不是按難度派，是按這件事需要什麼能力派。難度是結果，不是分類軸。

實作

照已定義的目標，讀既有程式、修改與驗證。

判斷

比較方案、review、核對證據與取捨。

機械處理

輸入與規則已完整，執行固定的轉換或整理。
「看起來簡單」不代表不用判斷。摘要若要篩選、查證、處理矛盾，就不是格式轉換。

派工還有一個與模型無關的理由

context 不是免費的倉庫，是模型的注意力預算。放太多東西進去，先壞的是判斷，再壞的是記憶，最後才是錢。

第一層，模型表現。context 越長，模型從裡面準確撈出資訊的能力越弱。這不是快滿了才變差，而是一路下滑，簡單任務也會。Anthropic 的工程文章把這叫 context rot：注意力要處理 n 個 token 之間 n² 組關係，預算有限。Chroma 測了 18 個模型，結論是「模型並不均勻地使用 context，輸入越長表現越不可靠」。幾千行測試輸出留在 main，就是拿雜訊稀釋後面每一個判斷。

第二層，壓縮失真。context 逼近上限時 Claude Code 會自動壓縮，把前面的對話摘要成一段。留什麼丟什麼由模型猜。官方文件寫得直接：過度壓縮會丟掉「當時看起來不重要、後來才發現關鍵」的細節。你前面拍板的決策、看過的行號，可能就在這一步變模糊，之後的推理建在殘缺的記憶上。

第三層才是錢。Claude Code 每一輪都重送整段對話，context 越胖，之後每一輪都跟著胖。第 6 章費用表裡那幾百萬個 cache read 就是這樣長出來的。

所以 subagent 在自己的 context window 裡工作這件事很重要。它讀過的檔案、測試輸出、搜尋結果都留在那裡，只有結果回到 main。要翻很多東西的工作，就算用同一顆模型，派出去也能讓 main 的對話保持乾淨。保護的是 main 的判斷品質，其次才是省錢。

main

分派實作範圍
收回結果
跑整合檢查

只有結果
subagent

讀既有程式
搜尋所有引用
跑一輪測試
比對契約文件
試錯、改、再跑
整理回報

同一件事的另一面

subagent 看不到 main 的對話歷史與已讀檔案。所以派工前要交代：

  1. 要完成什麼，邊界在哪。
  2. 子任務需要哪些資料與既有決策。
  3. 要回報什麼結果，主流程怎麼接回來。

這三條說不出來，就代表這段工作還在你腦子裡，不在票上。還在釐清方向、要反覆討論的工作，不要為了多模型而硬拆。

一個例外：fork 型 subagent 會繼承主對話的全部歷史，不必重講；但它的工具呼叫仍留在自己那邊，只有結果回 main。所以「main 保持乾淨」對兩種都成立，「看不到歷史、要交代三件事」只對一般 subagent 成立。第 5 章的示例是一般 subagent。

05接進 Claude Code

定義角色，再告訴主模型何時找它

不講 hook、不講攔截。一份 agent 定義加一段規則，就是我實作的全部骨架。

---
name: implementer
description: 實作已定義的功能，遵循既有程式慣例並回報驗證結果。
model: opus
effort: medium
---

重點是讓主模型知道何時找誰，而不只是資料夾裡多了一份定義。

欄位

name
角色名稱
description
何時適用。主模型靠這段決定要不要找它
model
使用模型
effort
推理投入。第 8 章獨立講

上面是去識別的示意設定，不是舊公司程式碼，也不能證明歷史任務實際跑了哪顆模型。實際執行模型要看當次紀錄。定義檔格式見官方文件「自訂 subagent」。

06真實案例

Fable 帶 subagent 完成一段資料遷移實作

既有系統要換一種資料儲存與讀取方式。這段工作包含雙寫、讀取端切換，以及契約文件與檢查。

  1. Fable main

    接到已拆好的功能票，依範圍分派實作。

  2. Opus workers

    分別完成雙寫、讀取端切換與文件工作。

  3. Fable main

    收回結果並跑整合檢查。

  4. Opus reviewer → Fable main

    reviewer 找到實作缺陷；Fable 根據 review 修正，再跑測試。

    1 failed / 92 passed→93 passed
  5. Sonnet checker

    檢查 PR 提案；不通過就修內容，再檢查到通過。這一步也有重試。

為什麼留失敗

派出去不會全部一次過。案例保留 review 後接縫測試先失敗、修正後通過的紀錄，因為接回來修正這一段才是 orchestrator 的工作。下一章的費用表包含這次失敗、重跑與 Sonnet 檢查的重試，沒有只挑成功輪次。

reviewer 是派工，不是顧問

第四步的 Opus reviewer 拿到的是一件有範圍的檢查工作：讀指定的改動、回報缺陷清單，結果由測試驗收。顧問處理的是 main 自己想不通的一題，回來的是意見，由人逐條裁決。兩者都能出判斷，差別在交出去的是工作還是問題。

已去識別

不展示原公司、repo、票號、客戶、業務欄位、路徑與截圖。模型、數字與成功／失敗狀態未改。

07這段工作，各模型用了多少

誰產生最多 output？單價較高的 output，也佔最多花費嗎？

單位：token
模型 一般 input output 快取讀取 快取寫入 累計
Fable 5
Opus 5
Sonnet 5
合計

input 是送給模型處理的內容，output 是模型產生的內容。快取寫入是儲存輸入供後續重用，不是模型寫程式。範圍只含上一章的實作、review、修正與提案檢查。

  • 單價5×

    output 單價確實較高。三個模型都是一般 input 的 5 倍：50÷10、25÷5、10÷2，美元／百萬 token。

  • 數量65.9%

    Opus 產生最多 output：222,751 ÷ 338,230。該組含實作與 code review，不是純寫程式的佔比。

  • 總花費73.9%

    但花費最多的是快取讀取。output 只佔 13.0%。重用輸入的累計量，超過了 output 較高單價帶來的花費。

這張表一定一起交代

  1. 累計 token 含反覆處理的快取內容。不是寫出了八千多萬個 token 的文字，也不是等量的不重複資料。
  2. 費用是 2026-09-10 官方標準 API 牌價等值，不是我實付的錢，也不能換算成省下多少訂閱額度。
  3. 部分速度欄位缺失，採標準價假設。每格各自四捨五入，顯示值相加可能與小計差一分錢。
  4. Fable 的協調、修正與保留脈絡本身有消耗。不能說 subagent 越多就越省。
  5. output 含推理 token，本表未拆推理與可見輸出。

不做「如果全部換成 Fable 會花多少」的假想對照。換模型後的工具步驟、輸出與快取行為都沒有量測。

08Opus 與 effort

型號之外，還有推理投入

回頭看第 5 章那行 effort: medium。同一顆 Opus，實作跟深度判斷我給不同的投入。

model

哪個模型承接工作。

effort

同一模型投入多少推理與回應工作。

  • 不必把 Opus 的所有任務固定在最高 effort。

  • 官方 Opus 5 指引：自己的評估顯示品質維持時用 low／medium，困難任務可提高。

  • effort 不是硬 token 上限，也不是可靠的字數控制。

  • effort 不是 Opus 獨有。著重 Opus 是因為它在我的分工裡承接實作與判斷。

界線

剛才的費用表不是 effort 對照實驗。不能拿它證明某個 effort 設定省多少，或品質不變。這是第二個旋鈕，不是第二個省錢承諾；要證明省多少，得自己做評估。

09延伸一句

同一套分工也能固化成 workflow

如果流程會重複跑，可以固化成 workflow，指定每個階段的模型。臨時產生的 dynamic workflow 同樣要留意實際派了誰，別不知不覺多出一支 Fable 艦隊。

不說 dynamic 必然昂貴，也不說固化就自動省額度。workflow 是進階題，今天只提這一句。

以上都是把工作派出去。
接下來換另一種做法：只借一次判斷。

共同點

不管手動派還是流程派，都要知道實際跑的是誰。角色名字不等於模型，看當次紀錄。

10advisor

我只需要你幫忙想這一題，不是接管整場工作

  1. 說清楚要判斷的問題，不是請顧問泛泛看一遍。

  2. 依問題選顧問，確認它能看到哪些資料。

  3. 決定提供什麼脈絡：挑現有答案的錯，或讓它不受答案影響地獨立想一遍。

  4. 收回意見，逐條採納、拒絕或標尚待查證。不是拿到建議就自動照做。

  5. 原本的執行流程繼續，不讓顧問不知不覺接管實作。

真實案例：給完整思路，反而困住顧問

設計自己的 advisor 用法時，我在兩個選項裡挑：給顧問摘要，或給完整對話。Web Pro 的回覆：

我原本在兩個選項裡挑，顧問指出我根本沒看到第三個。結果是加入盲審方式，顧問意見逐條裁決納入流程。

從這次諮詢帶走

  1. 要顧問挑現有答案的錯，與要顧問獨立想一遍，是不同問題。
  2. 提供更多脈絡不等於一定拿到更獨立的判斷。
  3. 顧問意見要回到資料與使用者決策，不因來自另一個模型就自動正確。

邊界

Web Pro、Codex 可以是顧問選項，不做排名或產品比較。顧問能不能自行讀資料，按實際路徑交代。這是我的用法，不與官方 API 的 advisor tool 混為同一產品。一次歷史事件，不是使用頻率統計，也不外推固定效果。

11收尾

不用先複製我的整套環境

三個問題，明天回去就能問自己。依現況誠實選：1 是還沒這樣想過，5 是已成為習慣。這只量你對三種做法的熟悉度，不量它們適不適合你手上的工作。

一段有明確邊界的工作，是否適合交給 subagent，而不是 main 從頭做到底？

使用 Opus 時，是否有意識地選 effort，而非每種任務都用同一檔？

某次判斷卡住時，是否需要借一次顧問意見，而不是讓它接管整場？

三題都選完後，這裡會標出你最不熟的一項，當作起點的建議。

不是少用強模型，而是知道哪一段值得用它。
派出去之後，仍然要接得回來。
