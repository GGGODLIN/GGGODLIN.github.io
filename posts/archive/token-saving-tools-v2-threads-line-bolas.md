最近這種主打「省 token／省 context」的工具一個接一個冒出來，數字都漂亮到不行。我用 Claude Code 是吃額度的，看到能省當然手癢，前後就裝了五個不同路線的來試：命令列代理、MCP server、壓縮輸出的 skill、語意檢索 MCP，還有最近最新的一個上下文壓縮層代理。

省流：五個裡只有一個我留著用，而且留它的原因根本不是省 token。剩下四個結論都一樣，省不了多少，代價反而在風險。

## 第一層：宣稱跟實測常常差一個量級

先講最直接的：這些工具報給你的省幅，跟你真正在意的省幅，常常是兩回事。

RTK（Rust Token Killer）是個命令列代理，攔 Bash 的輸出去截斷、過濾。它自己的報表兩天平均縮減 52.7%（穩態 30.8%），官方對外寫的是省 60-90%。聽起來很猛。但我拿 ccusage 對照真正送進模型的總 input，1.5 天 13.72M token 裡只省了 957K，真實 7.0%；對含 cache 的 fresh 算更只剩 2.94%。換算成錢大概 $2-4／1.5 天。報表那個 52.7% 跟你帳單上的 7% 差了一個量級，因為它算的是「砍掉多少輸出」，不是「整體送進模型少了多少」。

semble 那邊更誇張，同一個工具三個數字：dashboard 自報省 96%（基準是整檔讀），作者在 Show HN 公開的是 98%（基準是 grep+read），我早期做 A/B 實測真正省下來的是 32%（開 vs 不開成本 $4.06 vs $5.93）。從 96 掉到 32 差三倍。對 grep 基準那個 98% 也別當成它真實省幅，那是場景特定、還把 grep 的試錯成本全算進分母才撐得出來的數字。

context-mode 自報沙箱子行程 315KB 壓到 5.4KB 省 98%，這個倒是成立。問題在後面。

## 第二層：真正的代價是風險

省幅縮水其實還好，頂多就是沒省到。真正讓我把工具一個個拔掉的是風險，而且風險型態不只一種。

**第一種是有損的無聲降級。** RTK 截斷是真的會砍掉內容。`ps aux` 縮 98%（只留 CPU／記憶體最高那幾行）、`rtk grep` 預設上限 200 筆每行 80 字元，超過直接無聲砍掉、`rtk ls -la` 大目錄縮 50-70%。最陰的是模型完全不知道自己少看了什麼。它不會跟你說「這裡被截斷了」，它就拿著缺角的資料往下推，錯誤最後以「結論偏掉」「漏了某個行程」「漏比對某筆」的形式冒出來，事後超難歸因。我做的東西容錯很低，這種降級風險換那 7%，划不來。試了 1 天 13 小時就乾淨拔掉，留個備份、設四項重評條件，結案。

**第二種是裝了不穩定燒資源。** context-mode 這個 MCP server 我掛上去 132 個 session，真實採用 0 次。它四招扣到最後只剩沙箱子行程算新東西，但連這招也沒被自然選用。更慘的是它會生孤兒行程：5 天累積 18 個，其中 2 對卡進空轉迴圈各吃 98%／99% CPU，整機約 290% CPU，熱保護開始降頻、耗電 1.27%/min（正常 idle 才 0.2-0.4%/min）。我把它移除之後 load avg 從 10.29 掉到 4.81。它還有一排曾經被回報過的 issue：任意檔案讀取、shell injection、過度刪 settings.json 砍掉別人的 hook、忽略多帳號設定。2.5 個月發 165 版，差不多每天一發，regression 機率高得嚇人。順帶說一句，它 README 開頭那排 Microsoft／Google／Meta 的「在這些團隊使用中」logo，點下去全是空連結。

那它招牌那個「caveman 風格壓縮輸出省 65-75%」呢？這宣稱 2026-05-10 已經整支撤掉了（一個叫「retire prose-style enforcement entirely」的 commit），現在 README 第四支柱改成「不規範輸出文風」。引用的時候別當現行宣稱。

caveman 這個 skill 本身我也裝著，手法是砍掉 Claude 回覆裡的冠詞、填充、客套，自述省約 75%。結果 2026-05-30 我把全部 jsonl grep 過，呼叫紀錄 0 次，裝著從來沒被觸發過。理論上它最安全，因為只動 Claude 的輸出措辭、不碰你餵進去的資料，但能省的量級本來就小（單次回覆那點虛詞），代價是改變說話方式、犧牲對話深度。連它自己都內建一個 Auto-Clarity 例外：遇到安全警告、不可逆操作確認、多步驟序列怕被誤讀時就退出壓縮模式。等於工具自己承認壓縮在那些場合帶誤讀風險。

## 第三層：連更該有效的省法也省不了多少

那有人會說，那你換個更聰明的省法嘛，別去截斷輸出，去砍那些常駐載入的東西。聽起來合理，我也試著找一個「更該有效」的方向來比。結果它在省 token 這條軸上一樣贏不了 RTK 那點 7%。

| 省法 | 省的到底是什麼 | 量級（估計） |
|---|---|---|
| RTK | Bash 輸出的 fresh input token | 1.5 天省 957K（7%）、約 $2-4 |
| 清沒在用的 stdio MCP（13→6） | 啟動時間（schema 走 deferred pool 不進 prompt） | 省約 4-15 秒／次；省 token ≈ 0 |
| 控 always-on 的 skill 清單 | system prompt 常駐 token（本機約 6098 tok） | 走 cache_read（約 fresh 的 1/10）；砍一半 ≈ $0.2-0.4／天 |

清 MCP 那條根本不是省 token，省的是啟動時間（CC 的 MCP tool 走 deferred pool，schema 延後到 ToolSearch 才付，沒取用前近乎 0，只有 tool 名稱還佔少量 token）。唯一真省 prompt token 的是控 skill 清單，但它走了 prompt caching 之後，省下來的錢比 RTK 還少一個量級。（補一句準確度：本機這顆 skill 清單預算是自訂成 0.04／3072 的，CC 官方預設其實是 0.01／1536。）

所以「換個更有效的省法」這條退路也封死了。省 token 能做的空間本來就很小。至於唯一還算划算的方向，是把任務外包給更便宜的模型，那是另一篇的題目，這篇不展開。

## 壓軸：headroom 做對了透明可逆，結果還是不值得

前面四個多少都有點明顯毛病。最後這個 headroom 不一樣，它是五個裡最新的、唯一我親手裝起來 dry-run 量過效果跟資訊損失的，而且它在最關鍵的地方做對了。

它是個「上下文壓縮層」，把 tool 輸出、log、檔案、對話歷史在送進模型前先壓，宣稱省 60-95%、招牌數字是 90%。兩萬多星等級、Apache-2.0。

**先把公道給它。** headroom 的核心招數 CCR 是透明可逆的：它把一大塊內容搬走，原地留一張提貨單 `<<ccr:hash,size>>` 加上標題、url，模型看得到「這裡有東西、可以去領」，要用就呼叫 retrieve 把原文拉回來。這跟 RTK 直接刪行、模型不知道少了什麼的無聲截斷本質不同。在「透明 vs 無聲」這條軸上，headroom 明顯比 RTK 好一截，它是真的做對了的工具。

那省幅呢？我拿 47 筆真實 tool 輸出做 dry-run，用它自帶的 tiktoken 計數。base 不開 ML 只省 15.6% 毛省（47 筆裡只有 9 筆真被壓，集中在搜尋結果類，code read 那種 0%）。要衝到招牌的高省幅就得開 ML 那顆模型，開了之後 69.7% 毛省。但代價是把 inline 內容壓成「關鍵詞湯」，斷頭句加行號碎片，原本的內容存活大概 30%。招牌那個「省 90%」是 ML 那顆模型撐出來的，base 那 15.6% 攤到整條 input 上會更低，差不多就是 RTK 的量級。而且這還是毛省，真正的淨省要再扣掉模型之後去 retrieve 拉回來的 token。

不過真正壓垮它的跟壓縮品質沒關係，問題出在它的接法。headroom 最方便的接法是當 proxy，零改 code 接進去。問題是這個 proxy 要擺在 CC 連到 Anthropic 的主流量動脈上，所有流量都穿過它。這比 RTK 那種旁路 hook 重太多了：

- **單點故障**。它可不是薄薄一層轉發那麼簡單，裡頭是 FastAPI 加上預設要求的 Rust core 加上 CCR 的取回處理。這條死了你整個 CC 就斷。
- **Max 登入生死關**。轉址 `ANTHROPIC_BASE_URL` 得原封不動把 OAuth bearer 轉過去，多數 proxy 預設假設你走 API key，這會直接把 Max 登入搞掛。
- **跟 prompt caching 互斥，這點最尖銳**。壓縮會去改 prefix，prefix 一變 cache 全 miss。你省了 15% 的 token，卻丟掉 90% 的 cache 折扣，在 Max 上這是淨虧的。
- **紀錄會分岔**。CC 的 jsonl 存的是沒壓的版本，模型看到的是壓過的版本加 CCR hash 在 proxy 的記憶體裡，重啟一下那些 hash 就變成死掉的引用。

一個跟 RTK 差不多量級的安全省幅，要拿這一整包整合風險去換，這帳怎麼算都不划算。連一個做對了透明可逆、避開無聲降級的工具，最後都因為「安全的省只有 RTK 量級加整合風險加跟 caching 互斥」而被我退掉。連做對的都不值得，這就是「省 token 空間本來就小」最強的證據。

順帶提醒一個直覺陷阱：很多人會想「壓縮模型不夠強就換顆強的嘛」。headroom 這顆 ML 壓縮器 Kompress 是寫死架構的 ModernBERT 抽取式編碼器，逐 token 打分留高分丟低分，不是讀懂改寫，也換不成通用 LLM、本地小模型或線上便宜 API。這條路在它身上根本走不通。

### 順著 headroom 想下去：省 token 跟資訊損失其實是同一條軸

裝完 headroom 我反而想通一件之前沒講清楚的事。我以前一直把「省 token」跟「資訊損失」當成兩件事在權衡，好像可以省很多又完全保真。其實做不到。

可逆壓縮報的是搬走當下的毛省，真正的淨省是毛省減掉之後 retrieve 拉回來的那些。retrieve 率高就安全，但淨省縮水；retrieve 率低淨省接近毛省，但模型就在拿關鍵詞湯硬答，這又繞回無聲誤讀。「100 件只領 2 件」那種真省，只在清單型、掃過即棄的內容上成立（搜尋結果、log），而那正好就是 base 安全壓的那一種。ML 那個漂亮大數字，是硬把壓縮套到「你正在用」的內容上換來的（比方你正在改的那段 code），偏偏那裡最該 retrieve、不去領風險最高。

換句話說，每省一個 token，就是模型賭它之後不會回頭去讀那塊內容。只有那塊真的是冗餘，這個賭才安全。再疊上 Claude Code 本來就會選擇性讀（grep、分頁），加上 Max 既有的 prompt caching，可省的邊際比帳面上小很多。省很多又完全保真這件事，除非你省掉的本來就是冗餘，不然本質做不到。

## 反證：唯一留下的 semble，留它不是因為省 token

五個裡唯一我留著用的是 semble，一個語意檢索的 MCP。但它在「省 token」這件事上既誇大數字（96 vs 32），又量錯維度。

我留它的真正原因是它能做 grep 做不到的事：跨語言的概念檢索。手上專案後端是 ClojureScript、前端 TypeScript，一句自然語言的概念查詢能一次撈到兩端。grep 你得分語言搜、還得先知道確切的 symbol 名才搜得到。有一次靠它撈出一個橫跨前後端的篩選邏輯問題，semble 找到、Read 進去、最後修進一個合進主線的 PR。另一個例子是抓到一個字面上沒有 retry 字樣的延遲任務，語意命中、grep 完全抓不到。

它真正不可替代的是「grep 找不到的它找得到」，這是能力跟正確性的問題。省 token 只是順便的副產品。反過來剛好說明，省 token 從來就不是一個工具值得留下來的真正理由。

## 一句帶走

省 token 不該是你裝工具的理由。先問自己三件事：我到底在省哪種成本、省得到多少、要賠什麼。多數時候答案是省得有限、又要賠上無聲降級、燒機或整合風險，那就別裝。真要挑也挑「砍措辭不砍事實、隨時關得掉」的，但連這個動機本身常常都不夠強。

再深一層，省 token 多數時候就是拿資訊損失去換，這兩件事根本是同一條軸。真想認真省成本，等之後那篇講外包便宜模型的。
