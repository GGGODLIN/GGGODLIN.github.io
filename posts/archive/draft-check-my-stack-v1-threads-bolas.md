最近清點了一下：過去五週留檔深評過的工具有六十多個，每天還有好幾個看一眼就出局、連紀錄都懶得留的。六十多個裡面，值得走完整評估流程的不到二十個；走完的這些，絕大多數的結論是不裝，少數剩一點薄薄的、可以偷走的東西。

每週都在時間軸上刷到新的高星工具，「這個要不要看一下」變成高頻決策。這篇講我處理這個決策的方法，它是從一次具體的誤判修出來的。

## 第一輪就把順序做反

2026-05-15 評估 [planning-with-files](https://github.com/OthmanAdi/planning-with-files)（評估當時約 21K 星）。第一輪分析我先讀它的 README，列出 8 個值得借鑑的點，其中一項還被標成最高優先。深查之後，四個招牌賣點全部站不住：每一個我自己手上都已經有更整合的版本。

問題出在順序。先看工具的亮點、再回頭找自己哪裡可以對接，就會被亮點錨定，明明已經有的東西也會看成缺口。修出來的鐵律就一條：先列自己已經有什麼、各自多成熟，之後才把工具的賣點逐點對上去。順序強制，不能反。

## 你已經有的越多，新工具能給的越少

這條鐵律背後的帳很好算：一個工具對你的真實價值，要看你手上既有的等價物有多成熟。等價物越成熟，工具剩下能給你的越少。逐點對完之後就三種結果：

1. 你的更整合，剩不到什麼。絕大多數熱門工具落在這裡。
2. 工具的主打賣點正好是你反覆評估過、已經結案否決的路線。這比沒用更糟，因為認真評估它等於把已經付過的研究成本再付一次。
3. 少數真材實料。但留下來的多半是「偷它的架構設計、不裝它本身」，那是一個獨立的工作項，當不了引入工具的理由。

為什麼絕大多數落在第一種？我的解釋是：通用工具解決的是大眾市場的痛點，也就是「沒有一套紀律化的個人基礎設施」。skill、hook、memory、自動化這些東西一路累積下來之後，那個痛點在我這已經不存在了。先說清楚，這個前提對基礎設施還在起步的讀者不一定成立，你手上有的少，同一個工具可能真的有用；但「先盤點自己、再看工具」這個順序對任何人都成立，差在算出來的結果分布不同而已。

## ECC，學過它所以不再需要它

唯一親手裝過再移除的案例是 [affaan-m/ECC](https://github.com/affaan-m/ECC)（評估當時約 191K 星），2026-04-24 移除，有 commit 紀錄可查。2026-05-25 競品重評，確認了三件事。

第一，我現有的一部分東西本來就蒸餾自它：規則目錄源自 ECC，好幾個自製指令對得上它舊版的 changelog。學過它，借鑑那一輪早就做完了。第二，新版比當年裝的更大包，skill 從 119 個長到 232 個、agent 從 28 個長到 60 個，外加一個常駐控制平面，跟我「流程固化成 skill、不蓋一層大框架」的方向正好相反。第三，它主打的自動萃取記憶，撞上我反覆否決、已經結案的「讓 LLM 自動整併記憶」這條軸。

順帶看一下健康度訊號：1415 個 commit 對上第二名的 47 個，維護者高度集中；付費方案加贊助的商業漏斗很重；191K 星對一個配置大包來說異常地高。星數從來都當不了能力證據，之前看過 [graphify](https://github.com/safishamsi/graphify) 六週衝到 48K 星之後，異常成長的星數在我這一律先打折。

## 比沒用更糟的工具真的存在

[obsidian-second-brain](https://github.com/eugeniughelbur/obsidian-second-brain)（評估當時約 1.9K 星），43 個指令把筆記庫變成會自我改寫的 AI 第二大腦。周邊功能那些研究、行事曆、session 管理，我手上各有更整合的版本，沒什麼好說；致命的地方在它的差異化賣點本身：筆記自動改寫、自動整併、夜間 agent，正好就是我反覆否決、已經結案的那條「LLM 自動整併記憶」軸。差異化越強，對我越負。

同一條軸這段時間被不同包裝撞上好幾次：唯一親手用過再退役的 mempalace（這個部落格第一篇的主題），加上一串連裝都沒裝的紙上評估案，全是同一件事換衣服。有先例紀錄之後，第 N 次重撞的評估成本接近零，直接套結論就好。

## 流程後來固化成 skill，但它從來都帶著例外

這套方法後來固化成 [check-my-stack](https://github.com/gggodlin/check-my-stack) 這個 skill，六步：盤點自己（硬閘，讀 README 之前先做）、抽出工具的真實價值與健康度、逐點對照、真缺口檢查、殘值清單、收斂判決。

其中兩個容易被繞過的地方值得多講一句。一是盤點清單裡「試過又移除的工具，加上記錄在案的移除理由」是最強的訊號。二是真缺口檢查：工具補的空白不等於你的痛點。一個來源在自己管線裡壞了很久也沒人修，沒人修這件事本身就是「不重要」的證據，這種缺口工具補了你也不會用。

判決有三種：可改變現狀的候選、只剩薄殘值、純競品觀察。前兩種真的發生過：[Agent-Reach](https://github.com/Panniantong/Agent-Reach) 本體不裝，但抽走一個零依賴的公開 API 端點寫進自家管線；[alibaba/open-code-review](https://github.com/alibaba/open-code-review) 不採用，但它純資料加規則、不靠 LLM 的確定性工程層可以偷，已經衍生出自家工具的增強試用；[brooks-lint](https://github.com/hyhmrright/brooks-lint) 只被偷走 6 個分類學詞彙，嫁接進既有的 reviewer。流程輸出的是一個算出來的結果，從來都帶著例外，它管的只是順序跟誠實。

## 數字也要過同一關

我曾經登記過一個題目叫「我連續否決了 13 個 AI 記憶工具」，後來自己撤掉。復盤發現真正親手裝過、用過、再退役的記憶工具只有 mempalace 一個，其餘全是讀文件讀原始碼的紙上評估，連裝都沒裝。「否決 13 個」就是灌數字而已，差在誠不誠實。

所以這篇的計數全部帶範圍跟時點：日常快篩每天好幾個、不留紀錄；五週留檔深評六十多個具名工具；真正走完整流程的，截至 2026-06-11 先例紀錄累積 19 案，星數從 13 星到 191K 星，跨計畫管理、記憶、調度、程式碼審查好幾個領域。哪一層就寫哪一層，紙上評估就寫紙上評估。講究誠實對照的方法論，對自己的數字先要誠實。

## 清單本身才是資產

固化成 skill 的時候我跑了一個對照測試，想驗證「沒有這個 skill 的話 agent 會不會做」，結果發現測不出來：這套紀律已經滲進常駐記憶，在我這台機器上強模型本來就會先盤點再對照。所以 skill 的正當理由其實是可靠性，memory 會被裁切、誤刪、沒載入，skill 把方法變成不會丟、可以分享的東西，反觀「教 agent 一個它本來不會的招」這件事根本沒發生🤣

評估工具最大的成本也從來都在這裡：每次都從零開始研究。這套流程的副產品是把「自己有什麼」變成一份隨時可用的清單，每評一次就更新一次；先例紀錄讓同一條軸第 N 次被新包裝撞上時，幾乎不用再花成本。工具會一直冒出來，星數會一直暴漲，這份清單才是會增值的東西。
