# 省 token 工具：省不了多少 token，但風險不小

## 為什麼寫這篇

如果你用 Claude Code（或類似的 agent）想省額度、省錢，最近大概會看到一批主打「省 token／省 context」的工具，行銷數字都很漂亮：有的登上 Hacker News 高分、兩個多月發了上百個版本；有的在社群裡被以「少 75% token」傳播；有的 dashboard 直接自報省了 96%。看到這些數字，很容易就想動手裝來試。

我親自試過四個走不同路線的省 token 工具：命令列代理、MCP server、壓縮輸出的 skill、語意檢索的 MCP。每個都留下了完整的「宣稱數字 vs 實測數字 vs 下場」紀錄。試完之後，行銷數字不講的兩件事就浮出來了：

1. **宣稱與實測常差一個量級。** 工具報表或對外行銷的百分比，跟「對你真正在意的成本省了多少」往往不是同一回事。
2. **真正的代價在風險。** 砍事實的無聲降級、裝了之後不穩定燒資源——這些才是該擔心的，而不是省了幾個百分比。

兩條合起來，結論很簡單：省 token 能省下的那一點，多數時候不值得拿風險去換。

這篇只講這件事。「採用率才是工具的真跑分」「把任務外包給更便宜的模型」是另外兩篇的題目，這裡不搶。

---

## 四個工具，四種失準方式

先把四個工具擺出來。重點是它們「失準的方式」各不相同，不能硬塞進同一個框架：

- **RTK（Rust Token Killer）**：命令列代理，攔截 Bash 輸出做截斷／過濾。問題是省幅本身就低（對輸入只省 7%），而且是有損降級，最後我主動把它拔掉了——這不是「裝了沒人用」，是試用後因為風險和省幅都不夠而退役。
- **context-mode**：MCP server，宣稱用四招省 context。問題是宣稱 98%，但實際機器上不穩定（孤兒行程燒機），而且 132 個 session 裡真實採用 0 次。
- **caveman**：一個壓縮 Claude 輸出措辭的 skill。問題是它能省的本來就小（只壓縮輸出端的措辭），而且裝了從未被調用。
- **semble**：語意檢索的 MCP。問題是 dashboard 自報省 96%，但實測只有 32%（數字誇大）；而且它真正的價值根本不在省 token，在檢索。

下面分四層把這件事講清楚：省不了多少、代價在風險、連更該有效的省法也省不了多少、以及唯一被留用的工具留用的原因從來不是省 token。

---

## 第一層：省不了多少——宣稱與實測差一個量級

第一個要分清楚的，是「省幅」其實有兩種口徑，而它們常差一個量級：

1. **工具報表／對外宣稱口徑**：工具自己算「砍掉了多少輸出」，或對外行銷的百分比。
2. **對你真正在意的口徑**：送進模型的總量、或整體帳單，到底省了多少。

### RTK：報表 52.7%，對輸入只省 7%

RTK 的介接機制是一個全域 PreToolUse hook（針對 Bash 的 matcher），把每次 Bash 命令轉發給 `rtk hook claude` 處理，所以每一次 Bash 輸出都會被它攔下來截斷。試用的版本是 0.40.0。

它自己的報表（`rtk gain --daily`）顯示縮減率：5/20 是 73.5%、5/21 進入穩態是 30.8%，兩天平均 52.7%。官方對外宣稱則是「對常見開發命令省 60-90% token」。

但拿 ccusage 對照之後，對 Claude Code 的總輸入 token 真實只省了 7.0%（957K／13.72M）；如果把 cache create 也算進去（對 fresh input），只省 2.94%。成本上估計 1.5 天省下大約 $2-4。

工具報表 52.7%、官方宣稱 60-90%，對輸入真實 7%——這就是兩種口徑差一個量級的具體樣子。報表算的是「砍掉了多少 Bash 輸出」，但 Bash 輸出只佔整個對話送進模型總量的一小部分，所以反映到你真正付錢的維度上，就剩下 7%。

### semble：自報 96%，實測 32%

semble 的 dashboard 自報省了 96%（大約 1.4M token），但這個百分比的比較基準是「整檔 naive read」（每次都把整個檔案讀進來）。早期做的 A/B 實測——開 semble vs 不開——真實縮減大約 32%（成本 $4.06 vs $5.93）。

順帶一提，semble 在外部唯一公開的省幅數字是 98%，但那是針對「grep + read」這個基準（作者在 Show HN 的澄清），跟 dashboard 自報的 96%／1.4M 不是同一回事，後者只見於本機 dashboard，沒有外部佐證。

96% vs 32%，又是一個量級的差距。

### context-mode：宣稱 98%

context-mode 的官方宣稱裡，有兩條目前仍成立：ctx_execute 把沙箱子行程的輸出從 315 KB 壓到 5.4 KB，省 98%；think-in-code 的範例把 47 次 Read（700 KB）換成 1 次 ctx_execute（3.6 KB）。這兩條現行 README 都還在。

但它原本還宣稱過第四招——「用 caveman 風格壓縮輸出，省 65-75% 輸出 token」——這條**已經在 2026-05-10 整支移除**（對應的 commit 是「retire prose-style enforcement entirely」）。現行 README 的第四支柱已改成「不規範輸出文風」。所以這個 65-75% 是**曾宣稱、後撤回**的舊數字，不是現在的宣稱。

## 第二層：真正的代價在風險（全篇重心）

宣稱數字被誇大或量錯維度，頂多是「省得比想像少」。更重的問題是：省這一點要付出什麼代價。試下來，代價分兩種——砍事實的無聲降級、以及裝了之後不穩定燒資源。

### RTK：有損截斷的無聲降級

RTK 的截斷是有損的，而且是「無聲」的——模型不知道自己被砍掉了什麼。具體的例子：

- `ps aux` 縮 98%（只留下 CPU／記憶體最高的行程）。
- `rtk grep` 預設上限 200 筆、每行 80 字元，超過就無聲截斷。
- `rtk ls -la` 在大目錄縮 50-70%。

另外有一個數字值得注意：161 次解析器失敗時，它 100% 回退到原始輸出（沒有破壞），但解析成功時仍然是有損的。

無聲降級的危險在於：模型拿到被砍過的輸出，卻不知道少了什麼，於是錯誤會以「結論偏掉／漏看某個行程／漏掉某筆比對」的形式出現，而且事後很難歸因——你甚至不會意識到問題出在工具截斷。對容錯特別低的關鍵工作流，這種風險的代價遠超過那 7% 的省幅。

最後 RTK 在試用 1 天 13 小時（5/20-5/22）後退役，主因就是有損截斷對關鍵工作流的無聲降級風險太高，加上省幅本身也不足。退役時乾淨拔除、保留了 history.db 備份，並設了四項重新評估的觸發條件。

### context-mode：孤兒行程燒機

context-mode 的風險是另一種——裝了之後在機器上不穩定，會燒資源。實測 5 天累積了 18 個孤兒行程（9 對，每個 session 一對），其中 2 對進入空轉迴圈，各吃 98%／99% CPU。整機因此到大約 290% CPU，觸發 kernel_task 15% 的熱保護降頻，耗電達到 1.27%/min（正常閒置只有 0.2-0.4%/min）。移除（`claude mcp remove` 加上 `pkill -9`）之後，1 分鐘的 load avg 從 10.29 掉到 4.81。

除了燒機，context-mode 也曾有一批安全相關的 issue：任意檔案讀取沒有 deny-policy、ctx_insight 的字串插值有 shell injection 風險、PreToolUse hook 過度刪 settings.json 砍掉了旁邊的使用者 hook、忽略 CLAUDE_CONFIG_DIR 打到多帳號等等。考慮到它兩個多月發了上百個版本（近乎每天一個 release），regression 的機率不低。（這些 issue 的當前 open/closed 狀態未追，這裡用「曾有」的語氣描述。）

## 第三層：連「更該有效」的省法都省不了多少

到這裡可能會想：「那不要用有損工具，換一個更該有效的省法不就好了？」於是我去找一個比有損工具「更該有效」的省法來對照——砍常駐載入（系統 prompt 裡常駐的東西）。結果它在「省 token／省錢」這個維度上，也贏不了 RTK 那點 7%。

| 省法 | 省的是什麼 | 量級（估計） |
|---|---|---|
| RTK | Bash 輸出的 fresh input token | 1.5 天省 957K input（7%）、約 $2-4（大約 $1.3-2.7／天） |
| 清沒在用的 stdio MCP（13→6） | **啟動時間**（deferred pool 機制下 schema 不進 prompt） | 省 4-15 秒／次；**省 token 約等於 0** |
| 控 always-on skill 清單 | 系統 prompt 常駐 token（本機 6098 token） | 在 cache prefix 內走 cache_read（大約是 fresh 的十分之一）；砍一半大約 $0.2-0.4／天 |

兩個關鍵點需要說清楚：

**清 MCP 省的根本不是 token，是啟動時間。** Claude Code 的 MCP tool 走的是 deferred pool 機制——要到 ToolSearch 才取 schema，schema 不會直接列進系統 prompt。所以未取用前，schema 成本近乎 0（tool 的「名稱」仍然列在 system-reminder 裡，佔少量 token，所以不是絕對 0）。本機 2026-05-11 做過一次 MCP 清理：把 13 個 stdio（含一個 failed 的 pullmd，總連線 18）砍到 6 個 stdio（總連線 11），`claude mcp list` 的冷啟動從 10.55／10.68／21.33 秒降到 7.41／6.86／6.81 秒，省了大約 4-15 秒。這省的是啟動時間，不是 token。

這裡牽涉一個架構差異：stdio 的 MCP 啟動要 spawn 子行程、HTTP 的 MCP 只開一個 keep-alive socket，所以「加 stdio 才有啟動成本、加 HTTP 幾乎零成本」這個結論是成立的。至於具體的毫秒數（npx 1-2 秒、uvx 500 毫秒-1 秒、binary 50-100 毫秒、socket 10-100 毫秒），這些查不到權威 benchmark，屬於量級估計／經驗值，不是精確測量。

**唯一真正省 prompt token 的是 always-on skill 清單，但它走 cache 後省的錢比 RTK 還少一個量級。** always-on 的 skill 清單確實是真實的 prompt token 成本，由 settings.json 兩個 key 控制。本機實證：以 200K context 乘上 4%（注意，4% 是本機自訂值，官方預設是 0.01；見下面說明），上限是 8000 token；78 個啟用的 skill 吃掉 6098 token，達到上限的 76.2%。超過預算時 Claude Code 會把 description 截斷。

但這個成本是常駐在 cache prefix 裡的，走的是 cache_read（成本大約是 fresh 的十分之一）。就算把它砍一半，省下來的也只有大約每天 $0.2-0.4——比 RTK 那點省幅還少一個量級。

> 關於 skill 清單的預設值：官方預設是 skillListingBudgetFraction=0.01、maxSkillDescriptionChars=1536。本機用的 0.04／3072 是自訂的覆寫值，不是 Claude Code 的預設。上面的 76.2% 是本機自訂值下的實證百分比。

結論：清 MCP 省的根本不是 token（是啟動時間）；唯一真省 prompt token 的 skill 清單，走 prompt caching 之後省的錢又比 RTK 少一個量級。所以「那換個更有效的省法」這條退路也封死了——**省 token 能做的空間本來就很小**。既然空間本來就小，為它裝一個有損工具就更不划算。

（順帶一提：唯一還算划算的省 token 方向不在本篇——把任務外包給更便宜的模型，那是另一篇的題目。）

## 反證：唯一被留用的工具，留用的原因不是省 token

四個工具裡，唯一被留用的是 semble。而它被留下來的原因，恰好不是省 token。

前面講過，semble 在「省 token」這個維度上同時犯了兩個錯：**數字誇大**（自報 96% vs 實測 32%），而且**量錯維度**（真價值不在省 token）。它被留用的真正理由是——它能做 grep 做不到的跨語言概念橋接。

具體場景：某個專案的後端是 ClojureScript、前端是 TypeScript，用自然語言的概念查詢一次就能撈到兩端；換成 grep，要分語言搜，而且要先知道確切的 symbol 名稱才搜得到。semble 的這個能力有完整的證據鏈（不是玩具用法）：從 semble 檢索，到 Read，到一個已合併的 PR（一個跨語言檢索命中的修正）。另一個例子是抓到一個字面上沒有 retry 字樣的延遲任務——語意命中，grep 抓不到。

這正好翻轉了整篇的論點：semble 在「省 token」上既誇大又量錯維度，雙重失準，卻仍然被留用——因為它的價值在檢索，不在省 token。這恰恰證明：省 token 從來不是一個工具值得用的真正原因。

（附帶一提：這批工具裡 context-mode（0/132）、caveman（0 調用）屬於「裝了根本沒被自然拿起來用」。caveman 自述能省約 75% token，手法是丟掉填充詞、冠詞、客套，宣稱保留完整的技術準確度；但 2026-05-30 對全部 jsonl 做 grep，調用紀錄是 0 次。它的 SKILL.md 還在，但理論上最安全的工具卻沒人用。這種「採用率低本身也是一種省不到」——工具裝了一次都沒用，宣稱的省幅一次也沒兌現——只是這裡點到為止，採用率是另一篇的主軸。要再次強調：RTK 不算在這一類，它是試用後因省幅低加有損而主動拔掉，不是裝了沒人用。）

## 收尾

省 token 不該是裝工具的理由。三段收束的邏輯：

1. **省不了多少**——宣稱與實測常差一個量級（RTK 報表 52.7%／官方 60-90% vs 對輸入 7%；semble 96% vs 32%）。
2. **代價在風險**——有損工具是無聲降級（RTK 砍事實，模型不知道漏了什麼）、不穩定的工具會燒機（context-mode 孤兒行程 290% CPU）。省下的那一點，不值得拿風險去換。
3. **連退路都封死**——「那換個更該有效的省法」也省不了多少（砍常駐載入贏不了 RTK 的 7%），證明省 token 的空間本來就小；而唯一被留用的 semble，被採用的原因從來不是省 token，是它能做 grep 做不到的事。

所以裝工具之前，先問自己：「我到底在省哪一種成本、省得到多少、要賠什麼？」——多數時候答案是省得有限、又要賠風險，那就別裝。要用工具，就挑「砍措辭不砍事實、可以隨時關掉」的；但連這個動機本身，常常都不夠強。真要認真省 token，等之後那篇講「把任務外包給更便宜的模型」。
