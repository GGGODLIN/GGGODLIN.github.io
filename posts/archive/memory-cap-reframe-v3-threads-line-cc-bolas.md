# MEMORY.md 撞上限——我原本以為要砍字，後來才發現根本沒搞清楚問題

最近因為第三篇寫到撞 25KB 牆（完整脈絡在上一篇），讓我去認真查了一次三類解法到底各自是什麼。查完之後驚覺自己原本的直覺幾乎完全錯的——「上限太小就存少一點」，這個方向在我想像的是砍敘述，但真正有效的路根本不是這樣走的。

---

## A 類：直接調上限——不存在

我先把這個搞定：想找某個設定把上限調高，沒有。

官方文件把三個控制開關全列出來（自動記憶啟閉、儲存目錄、環境變數停用），沒有任何控制大小的選項，`autoMemoryMaxSize` / `autoMemoryMaxLines` 這種東西根本不存在。超出上限的部分官方原文寫得很清楚：「Content beyond that threshold is not loaded」，沒有後門，不是設定問題，是刻意的設計常數。

GitHub 上有兩個相關 issue 可以驗證官方態度。#40614（階層式記憶架構）2026-05-11 被標 CLOSED/NOT_PLANNED，#41283（孤兒記憶問題）同樣是 CLOSED/NOT_PLANNED。這個上限不是 bug，官方不修，也沒有公開的 binary 修補方式。

所以 A 類死路一條，跳過。

---

## B 類：旁路注入——可以用，但我沒選

這條路確實存在。機制是透過 SessionStart hook，把額外內容注入進每個 session 的情境，讓實際可用資訊量超過 25KB 的上限。原理是繞開，不是突破。

我理解這個方向之後本來有興趣，但看完副作用就決定先不走：

一、**靜默截斷**。旁路本身也有容量上界，超出的尾段直接掉掉，等於把原本的問題搬了個位置而已，沒有解掉。做工具的人自己也踩過這個坑。

二、**版本耦合**。CC 大概兩天更新一次，這套機制的走法是從某個特定版本觀察來的，機制可能靜默失效。你不知道它哪天就不動了。

三、**失效無警示**。hook 掛掉只是靜默缺了一段，你不會收到任何通知，要靠自己另外寫守護邏輯。

三個副作用裡最讓我猶豫的是「問題搬家」這個本質——如果資訊真的多到要靠旁路撐，先把 C 類走完才有意義。

---

## C 類：群集重組——數字說話

這才是讓我改變認知的那條路。

C 類不砍敘述，而是重組結構。把 MEMORY.md 從「一份平鋪的條目清單」改成「索引層 + 資訊層」的兩層設計：主索引只放群集入口，細節移到主題子檔案，Claude 需要的時候才用 Read 工具去讀對應檔案，不在 session 開頭預載。Anthropic 自己的官方文件裡其實直接寫明了這個設計意圖：「Claude keeps MEMORY.md concise by moving detailed notes into separate topic files」，按需載入。

我 2026-05-07 那次做了一次實際整理，數字如下：

整理前：34.7KB / 118 條，超出 24.4KB 注入上限大約 42%。

操作分三步：先刪 7 筆過時的條目，再重寫 28 條描述過長的條目（砍掉冗餘、保留錨點），最後把主索引做群集重組，建了 10 個群集入口、細節下放到子檔案。

整理後：17.7KB / 69 條 / 83 行。降幅 -49%，剩餘緩衝 7.3KB。

關鍵是：-49% 這個降幅，**主要來自最後那步群集重組，不是來自縮字數**。前兩步把描述寫短，效果是有，但佔比遠小於重組那步。

---

## 降 size ≠ 縮敘述

這是整件事讓我改觀的核心。

常見的直覺是：「上限卡在那裡，要塞更少 → 每條要寫短一點」。這個邏輯的隱含假設是，所有資訊都要留在 MEMORY.md 主索引裡。但如果你接受「主索引是導航層，細節在資訊層」這個設計，兩件事就分開了：降 size 是讓主索引變輕、讓 25KB 能裝更多導航指針；縮敘述是截掉資訊、讓每條內容變短。

一個是移位，一個是截斷，操作完全不同。

MEMORY.md 比較像圖書館目錄，不是書本身。目錄寫精簡是讓你能找到更多書，不是把書的內容刪掉。

---

## 決策順序

結論比較簡單：C 類走完才考慮 B 類，A 類不用考慮。

C 類「走完」的意思是：同主題群的條目都已做群集抽取，還有超出上限的條目是真的每個 session 都必須預載（而不是按需就夠）。這個條件滿足了，再去評估 B 類有沒有意義。

上 B 之前要先實證旁路容量（目前只有估計值，沒有官方文件），加截斷守護，限縮適用的 session 範圍，內容用固定檔案不帶動態資訊。沒把這些處理完就上，副作用原封不動在那裡。

---

官方態度是明的，兩個 issue 都 CLOSED/NOT_PLANNED，上限不會動。在這個前提下，把三類搞清楚反而讓事情簡單了——根本不用等，先把 C 走完就好。
