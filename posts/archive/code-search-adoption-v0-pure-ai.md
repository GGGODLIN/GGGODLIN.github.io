# 7 個前作全踩坑，第 8 個工具才突破採用率

過去兩個月，我在一個工作 repo 上連續埋了一連串「程式碼搜尋／探索」類的 MCP 工具。期待是：給 agent 多一個比 grep 更聰明的檢索工具，它寫程式時就會主動拿來用，省 token、找得更準。

實際結果是：採用率幾乎全部是 0。

我一度以為是工具不行。寫到最後我才確定，問題不在工具，而在一個更結構性的瓶頸——agent 對不熟的 MCP 工具天生保守，看到工具清單也不會主動拿來用，永遠退回 grep。一路埋到第 8 個工具，才第一次真正翻轉。這篇就把這 8 個工具的實測攤開來講，順著三層論點往下推：表層故事、中層的重新定義、以及一個核心命題——**工具的「能力」跟「會不會被採用」是兩件事，而採用率才是 agent 工具的真跑分**。

---

## 一、表層故事：埋了一連串工具，採用率幾乎全 0

先講最直接的觀察。在這個工作 repo 上，我前後裝起來裸測了三個程式碼搜尋工具，三戰三敗，採用率都是 0%。

**第一戰，一個走語意嵌入（semantic embedding）、後端接向量資料庫的工具。** 我針對 1206 個 session、共 531 MB 的 jsonl 做全量統計，它的 `search_code` 一共被呼叫 23 次，23 次全部回「No results found」，命中率 0%。後續 12 次重試全失敗，有 10 次直接退回 grep。索引本身是完整的（三個 repo 分別索引了三百多到四百多個檔、數千個 chunk），所以問題不在索引。

**第二戰，一個走子程序沙盒執行、加全文檢索（FTS5／BM25）再壓縮輸出的工具。** 跑了 5 天、132 個 session，真實的 tool_use 採用是 0 次。更糟的是它附帶一起事故：留下 18 個孤兒程序（9 對 ghost process），其中 2 對佔了 98% 和 99% 的 CPU，整機大約 290% CPU、每分鐘耗電 1.27%。把它移除後，1 分鐘 load average 從 10.29 掉回 4.81。

**第三戰，一個走 AST 語法樹圖譜（tree-sitter 剖析後存進 SQLite 再加 FTS5、做確定性圖遍歷）的工具。** 裸測 3 個 session，採用 0／64。

三個工具，三種不同的技術範式，結果一致：agent 看到清單，但不主動拿來用。第一直覺很自然——這些工具大概都不行。

---

## 二、重新定義：不是工具爛，是 agent 對不熟的工具天生保守

把三戰三敗放在一起看，共同的原因不是「每個工具都剛好選錯技術範式」，而是更上游的一件事：**Claude 對陌生的 MCP 工具預設保守，看到工具清單也不主動選，永遠退回 grep + Read。** 這是結構性的結論，不是個案。

最有說服力的證據來自第三個工具——那個走 AST 圖譜的工具。我後來給它加了引導提示，告訴 agent 該優先用它。加了之後，最佳場景（這個工具理論上最擅長的某個 repo）也只爬到 8／55 ≈ 14% 的採用率上限；換成另一個語言的場景則是 0／16。也就是說，即使換上理論上更適合的 AST 範式、又主動加了引導，採用率天花板還是只有 14%。這明顯不是演算法問題。

還有一個更細的訊號。這個工具實際上只有它的符號搜尋（走 FTS5 那條）被 agent 選用，而它真正主打的圖遍歷功能（呼叫鏈、被呼叫者、影響範圍、相關脈絡）完全沒被選過——偏偏 README 宣稱省 92% tool call 正是來自圖遍歷。換句話說，它最值錢的能力，對 Claude 的實際效用約等於 0。

後面我評估、但沒有實際裝起來跑的工具，也指向同一個結論：

- 一個同樣走 AST 圖形範式、提供 28 個 MCP 工具、還做社群偵測、支援多 repo 常駐的工具。我基於前面三戰三敗的結構性結論直接否決，沒啟動試用。它有 16,946 顆星——但星數是病毒式傳播的訊號，不是採用的訊號。
- 一個用純 C 寫成靜態執行檔、結合 AST + SQLite 知識圖、做型別解析、提供 14 個 MCP 工具的工具。它是同一個技術範式的第四個版本，設計再精緻也突破不了「agent 不主動選用」這個天花板；而且它有多個 SIGSEGV 的紅旗。

至此，故事的軸心轉了：從「工具爛」轉到「採用瓶頸」。歸因也清楚了——Claude 用不熟的工具失敗成本很高（參數猜錯、卡住、吐亂碼、白白燒掉預算），所以它預設退回熟悉的 grep + Read + Bash。

## 三、核心命題：能力 ≠ 採用，採用率才是真跑分

把前兩段收束成一句話：**工具「有沒有能力」跟「會不會被 agent 主動拿起來用」是兩件事。**

整條失敗脊上，每個工具的 README 都有亮眼的能力指標。前面那個 AST 工具宣稱省 92% tool call；那個純 C 工具的 arXiv 論文自稱在 31 個 repo 上達到 83% 的回答正確率、能在 3 分鐘內索引 2800 萬行的 Linux kernel。但實測下來，採用率落在 0% 到 14% 之間。那個 92% 省 tool call 的數字，全部來自圖遍歷，而圖遍歷的被選用率是 0——這是能力指標跟實際採用完全脫鉤的最直接案例。

高星數也不等於採用。前面那些工具裡，有 16,946 顆星的、有大約 2.5k 星（3 個月內累積）的、有大約 1,100 顆星的。這些都是傳播訊號，跟某一個使用者實際會不會用它，沒有關係。

那這件事有沒有人量？我去查了一輪，結論可以寫成弱化版：**主流的兩類跑分，都不把「選用型工具的主動採用率」當成被評測的維度。**

- code retrieval 類的跑分（例如 CodeSearchNet 用 MRR／NDCG、CoIR 用 NDCG@10）比的是檢索質量。
- agent tool-use 類的跑分（例如 BFCL 比 function call 正確率、τ-bench 比 pass^k 的任務完成率）比的是呼叫對不對。
- 連 2026 年 5 月一篇標題叫「Is Grep All You Need?」的 arXiv 論文，比的也是 grep 對上向量檢索的質量。

也就是說，這兩類跑分量的都是「工具被叫用之後表現如何」，而不是「agent 會不會主動把它拿起來用」。連 semble 自己對外的 Show HN 標語都是「比 grep 省 98% token」——還是拿 token 數字來行銷。

而「agent 不主動用 MCP 工具、退回 grep」本身是個公認的現象，不是我一個人的個案：ast-grep 的維護者、相關技術文章、Hacker News 討論、以及前面那篇 arXiv 論文都記錄過。公認的根因是兩個：一是訓練資料裡 grep 太熟悉，二是缺乏明確指令叫 agent 改用新工具。這反過來說明——採用率才是該被量、但目前沒被當成跑分維度的那件事。

把前面兩段合起來，就得到這篇可以帶走的重新定義：**採用率才是 agent 工具的真跑分。**

## 四、破關：第 8 個工具怎麼突破——破的不是演算法，是兩個成分

semble 是這條失敗脊之後第一個被「自然採用」的工具，也就是第 8 個。它突破靠的不是更強的演算法，是兩個成分。

先看採用數據（用工作 repo 的 jsonl 做 grep 統計，再跟 semble 自己 dashboard 上「全期 33」的數字交叉驗證，兩邊一致）：

- 全期 33 次 MCP 呼叫（32 次 search、1 次 find_related）、跨 8 個 session。
- 排除掉 A/B 控制組和 resume 的 session 之後，**自然工作期是 25 次呼叫 / 6 個 session**（5/22–5/28）。
- 在這 6 個 session 裡，有 2 個 session 它是 agent 的首選動作（first-move），而且沒有任何一個 session 完全忽略它。

更重要的是它真的進到生產：有一次它命中後接著 Read、最後改動上了一個合併進主線的 PR——是 semble → Read → 上線的完整鏈，不是玩具用法。

突破的兩個成分：

1. **夠輕的靜態嵌入（屬於工具效能軸）。** semble 用一種靜態嵌入模型（純 CPU 也跑得快、不用養一個常駐服務），再加上 BM25 融合與排序加權。這讓檢索質量「夠好」。
2. **一句明確指令（屬於採用軸，也是真正的槓桿）。** 我把一句指令寫進該 repo 的本機指令檔（這是 CC 原生會載入的路徑，附加在主指令檔之後），明確叫 agent 優先用它取代 grep。

我原本設計的是「三招全開」——MCP + 指令 + subagent。實際只有「MCP + 指令」有效；subagent 那條完全沒派工，0 次，後來砍掉了。這點下面還會再講。

## 五、誠實數字：省 96% 是自報，實測約 32%；真價值在 polyglot 概念橋接

關於「省 token」，我要把口徑說清楚，因為這裡很容易誤導。

- **96%：dashboard 自報值。** semble 自己的 dashboard 報它省了 96% token、大約省了 140 萬。但這是拿「整個檔案直接讀進來」當基準的樂觀比較。
- **32%：A/B 實測值。** 早期我做過一組 A/B：用 semble 的那組花了 $4.06，沒用的那組花了 $5.93，實際省下來大約 32%。
- **98%：對外行銷值。** semble 的 Show HN 標語寫的是「比 grep 省 98% token」，這是拿 grep 當比較基準的行銷數字。

三個數字三種比較基準，不能混為一談。本篇主述以 32% 的實測值為準。

更關鍵的是：**semble 的真價值其實不在省 token，而在跨語言（polyglot）的概念橋接。**

這個工作 repo 是個跨語言專案：後端用 ClojureScript、前端用 TypeScript。grep 要能搜中，你得先知道確切的 symbol 名稱，而且還得分語言各搜一次。semble 讓我用一句自然語言的概念查詢，一次就撈到跨語言兩端的相關檔。實際幾個案例：

- 一個跨前後端的篩選 bug：semble 一次命中前端的查詢檔與後端的核心檔，順著修，最後上了那個合併進主線的 PR。
- 一個第三方金流重試的延遲任務：那個任務的名字裡根本沒有「retry」這個字，grep 抓不到，但 semble 靠語意命中了，6 次查詢 6 次正確。
- 一個關於 carrier service 的問題：first-move 就直接命中使用者問的那個前端檔，外加後端的對應檔。
- 中英混合查詢也行（例如把中文操作描述跟英文 API 名混在一起查）。

這才是 grep 補不上的點，也是我願意留下 semble 的真正理由——不是因為它省了多少 token。

## 六、方法論：把三軸分開歸因

從這整段經驗裡，我抽出一個可複用的判準：評估這類工具時，要把三個軸分開歸因，每個功能先歸軸、再判定。

1. **採用軸（agent 會不會自發選用）。** 槓桿是寫進指令檔（`CLAUDE.md` / `AGENTS.md`）的明確指令，例如「優先用 X 取代 grep」。
2. **脈絡效率軸（搜尋的中間結果會不會污染主 context）。** 槓桿是用 subagent 包起來——讓中間結果留在 subagent 的 context 裡，主 session 只拿摘要回來。
3. **工具效能軸（檢索質量、速度、索引成本）。** 槓桿是工具本身的設計（semantic vs BM25 vs AST graph、嵌入質量、靜態 vs transformer 模型）。

這裡有一個反直覺、但很重要的點：**subagent 並不解決採用問題。** 派一個 subagent，跟選一個 MCP 工具，走的是同一個決策機制——agent 看 description 自己判斷要不要叫用。而且 Claude 對不熟的 subagent 預設更保守，加上派工是一次不可回收的脈絡交接，所以門檻其實更高，不是更低。semble 的 subagent 那條 0 次派工，正好是這條規則的實證。

## 七、我自己也踩了同一個盲點

最後要補一段誠實的閉環：在設計 semble 的試用時，我自己就掉進了「能力 ≠ 採用」這個陷阱。

最初的 v0 設計，我的基準組只開了 MCP 的頂層工具——但這等於沒有測「採用率」這個假設（而採用率為 0 這件事，前面三個工具已經驗證過三次了）。後來是被使用者戳破，我才把設計改成「三招全開」，真正去測「指令」這個採用槓桿。

對應到上面的方法論，當時還有一個典型的三軸混淆錯誤：以為「semble 提供了 subagent 這條路，所以就解決了採用問題」。但前面已經說過——subagent 不解採用。

所以連設計這個實驗的人，都會在第一版掉進這個盲點。這也正好說明，「能力 ≠ 採用」不是一個只有別人會犯的錯，而是一個相當普遍的認知陷阱。

## 一點補充與邊界

幾個我沒法從數據裡證明、必須誠實標明的地方：

- semble 的突破到底「檢索質量夠好」貢獻多少、「指令槓桿」貢獻多少，我沒辦法純從數據拆開——這兩個成分是同時上場的，沒有單獨的控制組。
- semble 採用率跟前面那個 AST 工具 14% 的天花板，並不是同一個 repo、同一個場景下的嚴格對照（那個 14% 是另一個 repo 加引導提示的結果），所以不能宣稱「同條件下 semble 贏過它」。
- 這次試用只有 10 天、單一 repo，長期的穩定性（質量會不會漂移、會不會累積 ghost process）還需要再觀察一輪，目前不宜宣稱長期可靠。
- semble 也有它的限制：find_related 全期只被叫用 1 次（33 次裡的 1 次），它的圖／關聯功能對 Claude 的效用幾乎是 0，跟前面那個 AST 工具「只用得到符號搜尋」是同一個模式。另外它不讀 `.git/info/exclude`，只讀 `.gitignore` 和 `.sembleignore`，所以在 worktree 環境下會重複索引，得加一個 `.sembleignore` 才修掉。
- 外部的技術宣稱（嵌入模型、版本號、各工具星數、那篇 arXiv 論文自稱的基準）都是轉述自各家 repo／README／預印本，我沒有獨立查證，一律當「單一來源」看待。
