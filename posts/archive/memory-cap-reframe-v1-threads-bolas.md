前一篇寫 MEMORY.md 撞牆的完整脈絡，撞牆當天直接觸發整理——34.7KB、118 條、超出注入上限 42%，系統警告說「只載入了一部分」，但沒說少了哪幾條。

那次整理完之後我才搞清楚，面對 25KB 上限，能走的路只有三類，而多數人預設的第一直覺根本是個假選項。

---

## A 類不存在，這條路不用考慮

最直覺的反應是：有沒有辦法讓 CC 多載一點？調個設定、改個參數？

答案是沒有，而且不是 bug，是刻意設計的。

官方文件原文：「Content beyond that threshold is not loaded at session start」。設定文件列的選項只有三個：開關記憶體功能、指定目錄、全域停用，**沒有任何調整上限的設定**（`autoMemoryMaxSize` 之類的選項不存在）。

GitHub 上有人開過 issue——#40614 要 hierarchical memory、#41283 處理 orphaned memory，兩個都是 CLOSED/NOT_PLANNED。二進位檔裡還寫死了一句「MEMORY.md 請控制在 200 行以內」，態度很明確。

所以 A 類（真的突破 25KB）窮舉確認不存在，2026-05-30 重核官方文件，結論沒變。清楚了就不浪費時間在這裡，直接看 B 和 C。

---

## B 類有選項，但代價比你想的多

B 類的邏輯是：上限不動，用 hook 從旁路額外注入內容，讓每次 session 實際載到的東西超過 25KB。

SessionStart hook 有個 `additionalContext` 欄位確實能真正進入對話脈絡（不是只顯示在 terminal），社群也有幾個工具在走這條路。

看起來很美，但我研究完之後沒選 B，原因有三個副作用：

一是**靜默截斷**。旁路注入本身也有容量上限，超出那個上限的尾段無警告丟失——原本 25KB 截斷的問題搬到另一個地方，沒有解掉。

二是**版本耦合**。走哪條路徑的機制是在特定版本觀察到的，CC 大約每兩天更新一次，機制可能靜默失效。

三是**失效無警示**。hook 掛掉只會靜默少一段，要自己另外寫守護，不然你根本不知道某次 session 少了什麼。

這三點加在一起，就是「把問題搬家、然後需要再工程化」。如果 C 類還沒走完，沒理由先跑去碰 B。

---

## C 類才是真正的解：降 size 不等於縮敘述

我一開始以為「檔案太大就是每條描述太長、砍字數」，後來整理完才發現根本不是這樣。

正確拆解是：「縮敘述」是每條條目的字數變少，資訊損失。「降 size」是整體檔案變小，但可以透過**移位**而不是**截斷**達成。

官方設計意圖說得很清楚：「Claude keeps MEMORY.md concise by moving detailed notes into separate topic files. Topic files are not loaded at startup. Claude reads them on demand.」

白話就是：MEMORY.md 是目錄，不是書本身。目錄精簡讓你能放更多索引，細節在另外的主題檔裡，需要時才讀，不佔注入配額。

2026-05-07 那次整理是實證——先刪了 7 筆真的過時的條目，再重寫 28 條過長的描述把冗餘砍掉，最後重組分群、建 10 個群集索引、細節下放各自的主題檔。

結果：34.7KB 降到 17.7KB，條目 118 條降到 69 條，**降幅 -49%**，距上限剩 7.3KB 緩衝。

這個 -49% 的降幅，絕大部分來自最後那步重組分群，不是靠砍字數來的。砍字數那步也做了，但對總 size 的貢獻遠比重組小。

---

## 決策規則很簡單

C 類先走完。「走完」的判準是：同主題群的條目都已經做過群集抽取，而且剩下還超出 25KB 的是真的每次 session 都必須載入的東西，不是按需載入就夠。

達到這個判準之後才評估 B，而且要先實證旁路注入的真實容量（目前有估計數字但未驗），加截斷守護，並限縮適用場景（不要讓它在 headless 執行的場合也一起注入）。

A 類不考慮，確認不存在了。

三類搞清楚之後，「記憶體裡到底塞了什麼」和「這條 entry 有沒有必要在主索引裡」這兩個問題才會問得準。

降 size 不是把話講少，是把細節放對地方。
