# 你已經有的越多，新工具能給的越少

五月中評估 [planning-with-files](https://github.com/OthmanAdi/planning-with-files)（評估當時約 21K 星）的時候，我第一輪分析就把順序做反了。先讀 README，列出 8 個可以借鑑的點，其中一個還被我標成最高優先；回頭深查，四個招牌功能在我這邊全部站不住，連那個最高優先也是誤判。問題出在順序：先看工具亮點、再回頭找自己哪裡能對接，人就會被亮點錨定，看什麼都像缺口。

那次誤判之後我把規則修成死的：評任何工具，第一步先列自己在那個領域已經有什麼、各自多成熟，列完才准打開工具的 README。然後每個賣點對上去問同一句話：我手上已有的版本，差它多少？多數時候答案是「剩不到什麼」。整套方法一句話講完：你已經有的越多，新工具能給的越少。

為什麼多數熱門工具在我這邊都剩不到什麼？我的解釋是，通用工具解的是大眾市場的痛點：「沒有一套紀律化的個人基礎設施」。skill、hook、記憶、自動化都自己建過一輪的人，這個痛點已經不存在，工具能給的自然薄。這個前提倒不是人人成立，基礎設施還在起步的讀者，同一套順序照用，結論分布會很不一樣，搞不好真的有用。但「先盤點自己、再看工具」這個順序對任何人都成立。

對完之後結果有三種，沒有裝或不裝的二分：

1. 剩不到什麼：你已有的版本更整合，工具降級成競品觀察。
2. 比沒用更糟：工具重新翻案一條你已經反覆否決、結案的路線，評估它等於把付過的研究成本再付一次。
3. 薄殘值：少數真材實料，但殘值多半是「偷它的架構設計、不裝它本體」，是一個獨立工作項，當不了引入工具的理由。

第二種值得展開講。[obsidian-second-brain](https://github.com/eugeniughelbur/obsidian-second-brain)（評估當時約 1.9K 星）用 43 個指令把筆記庫變成會自我改寫的 AI 第二大腦。周邊功能像研究、行事曆、session 管理，我這邊都有更整合的版本，這沒什麼。致命的是它的差異化賣點本身：筆記自我改寫、自動整併、夜間 agent，正好是我反覆否決、早就結案的「讓 LLM 自動整併記憶」這條軸。同一條軸先後被好幾個不同包裝撞上，親手用過再退役的只有第一篇寫過的那個向量記憶系統，其餘全是紙上看完直接套已有結論。差異化越強，在我這邊越扣分，這種工具評起來最快。

親手裝過再移除的最完整案例是 [ECC](https://github.com/affaan-m/ECC)（評估當時約 191K 星），2026-04-24 移除，有 commit 紀錄。一個月後競品重評，發現三件事。第一，我現有的一部分規則目錄根本蒸餾自它，借鑑早就做完一輪。第二，新版比當年裝的更大包，skill 從 119 個膨脹到 232 個、agent 從 28 個變 60 個，外加常駐控制平面，跟我「流程固化成 skill、不蓋大框架」的方向相反。第三，主打的自動萃取功能又撞上面那條已結案的記憶整併軸。順帶看健康度訊號：commit 數第一名 1415、第二名 47，加上付費方案和贊助漏斗，191K 星對一個配置包來說異常高，這種星數我一律打折看。星數本來就是動態值，另一個工具在我紀錄裡舊記約 1,110 星、三週後查證是 33,927，是暴漲還是當初誤記，已經無法分辨了。

流程本身固化成了 [check-my-stack](https://github.com/gggodlin/check-my-stack) 這個 skill。六個步驟可以壓成三句：一個硬閘（盤點自己，先做，其中「試過又移除的工具加記錄在案的理由」是最強訊號）、一個問法（每個賣點問「我已有的版本差它多少」）、一張反面清單（先列亮點再找對接、星數當能力證據、沒對到真缺口就喊補缺口、虛構先例校準，全是犯過或差點犯的）。

頻率才是需要固化的原因。時間軸上每天刷到的新工具我快篩好幾個，看一眼出局、不留紀錄；過去五週留檔深評的具名工具六十多個；其中值得走完整框架的，截至 2026-06-11 累積 19 案。沒有固定流程，這個量每次都從零開始研究，撐不住。

兩個容易繞過框架的話術也記一下。第一個是「它有我沒有」：工具補的空白不等於你的痛點。評 [qiaomu-anything-to-notebooklm](https://github.com/joeseesun/qiaomu-anything-to-notebooklm) 那次，我口述的缺口跟工具實際補的缺口根本兩回事，先把缺口歸對類再判斷。它還宣稱 6 層級聯處理，讀原始碼發現兩層是到不了的死碼，實際約 4 層，宣稱的層數要讀控制流驗證。第二個是把「沒覆蓋」當「有痛」：評 [Agent-Reach](https://github.com/Panniantong/Agent-Reach) 時發現我管線裡有個來源壞了很久也沒人修，這個沒人修本身就是「不重要」的證據。

但這套框架也當不了否決機。Agent-Reach 本體不裝，我抽了其中一個零依賴的公開 API 端點寫進自家管線；[open-code-review](https://github.com/alibaba/open-code-review) 不採用，但它那層純資料加規則、不靠 LLM 的確定性工程可以偷，已經衍生出自家工具的增強試用；[brooks-lint](https://github.com/hyhmrright/brooks-lint) 只偷了 6 個分類學詞彙，嫁接進既有的程式碼審查工具。判決有三種，部分採用真實存在，只是罕見。

計數也要誠實。我曾經登記過一個題目「我連續否決了 13 個 AI 記憶工具」，復盤之後撤掉了：真正親手裝過、用過、再否決的記憶工具只有一個，其餘全是紙上評估，連裝都沒裝。「否決 13 個」是灌數字，同軸否決的次數冒充不了親身踩坑數。這套方法多數時候就是紙上評估紀律：讀文件、讀原始碼、查 repo 健康度，然後判斷。寫成文章也照這個口徑寫。

最後一筆有點好笑：把方法固化成 skill 的時候，照寫 skill 的流程跑了一次「沒有 skill 的基線測試」，結果測不出差異🤣 因為這套紀律早就滲進常駐記憶，模型在我這台機器上本來就會先盤點再對照。所以 skill 的正當理由是可靠性（記憶會被裁切、誤刪、沒載入）跟可維護、可分享，教 agent 新把戲反而排不上。固化這個動作本身，也過了一遍同一種檢驗。

裝錯工具不貴，貴的是每次都從零開始研究。先例紀錄讓同一條軸第 N 次被不同包裝撞上時，成本趨近於零，直接套結論就好。框架的副產品是把「自己有什麼」變成一份隨時可用的清單，每次評估都在讓這份清單增值。先把自己有什麼列清楚，多數熱門工具會自己掉出名單。供大家參考。
