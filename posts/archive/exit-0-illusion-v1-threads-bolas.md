最近在研究一個問題：為什麼派出去的工作代理老是幻造結果。

研究到一半，我派出去負責研究的工具本身幻造了兩次。

第一次，我叫它從 36 條清單裡抽 12 個樣本對應回原始紀錄，它回傳的清單裡原本 #1 的案例變成別的、#7 的案例變成別的、#21 的案例也變成別的——全錯位，但格式工整、沒有任何警告。

第二次，同一個工具再派一次，它在回應裡說自己無法執行是因為看到一條 constraint：「CRITICAL: Respond with TEXT ONLY」。那條 prompt 裡根本不存在這個東西，它自己捏的。

這就是這篇要講的事。

---

## 報告層成功，結果層呢？

在 LLM 工具鏈裡，有兩層信號會告訴你任務完成了。

**報告層**：exit code 是 0、stdout 印出 success、log 說「detected X」、工作代理回傳「我做完了」、系統服務說 running。

**結果層**：執行檔真的在 PATH 裡、工件真的存在、程序真的在主迴圈跑著、格式解析端真的認識輸出格式、目標檔案真的被改到。

這兩層之間的差距，我一個月裡撞到大約 30 個案例，跨了 10 個不同的工作 session。問題不是偶爾出現，而且不只出現在一種機制上。

---

## 四種主要形式

這個差距在我的使用情境裡大致分成四類：

**A — 工作代理直接編造**：代理報告找到某段程式碼、某個函式、某個翻譯 key，實際上那些東西根本不存在。最大宗，我遇到大概 8 個案例。

**B — 安裝靜默失敗**：工具指令回傳 exit 0，實際上執行檔沒裝進去。5 個案例。

**C — 排程任務名義啟動**：設定好的排程或背景工作「running」，實際上每次跑的都是 NOOP，或者卡在某個前置條件一直過不了。5 個案例。

**D — 探針通過但測的不是真實路徑**：用一個小型探針驗證某個行為，探針說失敗，就宣稱找到了鐵證；但探針的設定和真實運行環境根本不一樣。5 個案例。

---

## 四個具體的樣子

**A 的樣子**：5 月 20 日，我叫代理去找一個 CVS 取貨限制的實作位置。它回報找到了：`product.quantity_limit.total_limit`、`t('cvs.quantity_limit.*')`、`QuantityLimitHelp.tsx`。這些檔案、這些 key，沒有一個真的存在。它描述得相當確定，給了完整的路徑和函式名稱，然後全錯。

**C 的樣子**：5 月 18 日，我設好一個每日排程任務要自動執行某個個人管理流程。系統說在跑、狀態 running、等待觀察中。結果是：每次的前置條件偵測都正確判定「沒有真實變動」然後 NOOP，一旦偵測到真的要 GO 又會 rollback。整個月，一次都沒有真正跑完過。零進展，安安靜靜的。

**B 的樣子**：5 月 20 日，`uv install aider` 執行完，exit 0。但那台機器的 Python 3.14 沒有對應的 scipy wheel，`which aider` 找不到，`uv tool list` 也沒有它。安裝成功的樣子，沒有安裝成功的結果。

**D 的樣子**：5 月 20 日，我用一個 61 字的探針打某個 API 伺服器，設定 `stream:false`，失敗了。然後宣稱「parser broken，鐵證」。但同一台伺服器、同一個設定，真實運行環境是 `stream:true`，拿到了 118 個結構化輸出。探針測的根本不是真實路徑在走的那條路。

## 小丑竟是我自己

這篇開頭提到的兩個案例，是 ~30 個裡唯一在「寫這篇文章的當下」發生的。

我在研究「為什麼代理會幻造」，然後派出去做研究的工具幻造了兩次——一次錯位清單、一次捏造限制條件。我現在的狀態是：一邊觀察到現象、一邊親身成為現象的素材。

就因為它幻造了，這篇才寫得出來。

---

## Anthropic 知道，而且不修

我以為這是 bug，等一下就會修。

查了一下發現不是。

Anthropic 的 GitHub 上有 4 個直接相關的 issue，全數關閉不修：

- [#17995](https://github.com/anthropics/claude-code/issues/17995)：Task tool 工作代理工具被拒時幻造輸出
- [#21585](https://github.com/anthropics/claude-code/issues/21585)：`subagent_type="Bash"` 幻造命令輸出（標記為重複）
- [#24542](https://github.com/anthropics/claude-code/issues/24542)：沒有 Bash 存取的代理靜默幻造（標記 bug / area:security，關閉為 #17995 重複）
- [#5812](https://github.com/anthropics/claude-code/issues/5812)：功能請求：允許 hook 在工作代理和主 session 之間橋接脈絡（關閉不修）

[官方文件](https://code.claude.com/docs/en/sub-agents)的 line 766-770 明確寫：Explore 和 Plan 這兩個內建代理會略過使用者的設定檔和記憶體。

他們把這個定性為設計選擇，不是 bug。工作代理隔離優於脈絡共享——幻造是這個選擇的副作用。

---

## 根因三層

**第一層：零脈絡的工作者**

每個工作代理以全新脈絡啟動：看不到對話歷史、看不到我的設定檔、看不到任何記憶體。Explore 和 Plan 是唯一完全略過使用者設定的代理，而且沒有前端設定可以改這個行為。

一個對工作環境一無所知的工作者去做高度依賴脈絡的任務，結果就是這樣。

**第二層：同時降兩級**

Anthropic 預設讓 Explore 用它們家比較小的那個模型——Haiku。而主 session 同時可能跑在能力最強的那個。我在本次 session 的代理逐字稿裡看到 model 欄位的確認。

派 Explore 等於同時發生兩件事：脈絡從完整降到零，模型能力從最強降到最輕量。這是兩個維度同時跌落。

**第三層：LLM 天性是補通順**

這層解釋「為什麼會幻造」的另一面：模型寧可補一個合理答案，也不會說「我做不到」。

LLM 的天性是把輸入補成通順的輸出。代理寫不到真實資料，就補一個格式正確的假資料；模型不會呼叫工具，就用文字模擬工具呼叫的樣子；代理不認識一個限制條件，就捏造一個 quote 然後拒絕執行。這是模型本質決定的行為，把它當 bug 修就搞錯地方了。

前兩層解釋「為什麼會幻造」，第三層解釋「為什麼不告訴你它在幻造」。

## 我自己的兩條方向

修復不會從 Anthropic 那邊來，已經確認了。

**派工側**：問題根因是讓「沒有脈絡的工作者」去做「需要脈絡的任務」。我的回應是阻止這件事：把那個會略過所有設定的內建代理加進禁止清單，為「需要脈絡的搜索任務」另開一條會繼承完整脈絡的代理路徑。同時我補上了 7 條「即使觸發了派工條件也不該派」的原則——原本的派工規則只說「什麼情況該派誰」，沒說「什麼情況不管怎樣都不要派」，這個漏洞讓很多案例從縫隙裡掉出去。

**確認側**：報告層的宣告我現在不接受了。不接受「測過了」、不接受「應該 OK」、不接受「works as expected」。改成逐項對照：我預期會看到什麼 / 實際看到什麼 / 匹配嗎？對結果層做驗證，不看報告層的聲明。

實作細節另出一篇，這篇只說到這。

---

## 帶走兩個判準

**判準一，要不要派**：「這個任務如果沒看過我的設定、我的脈絡、我的既有清單，能做得出來嗎？」做不出來，main session 自己做，或用能繼承完整脈絡的代理。做得出來，派沒問題。

這個判準也適用在安裝、排程、探針——這三類的根因都是「執行者沒看到真實環境」。報告層 exit 0 沒看到 PATH、排程 running 沒看到真實 delta、探針設定沒看到真實請求形狀。

**判準二，怎麼確認完成**：預期看到什麼 / 實際看到什麼 / 匹配嗎。重點在兩層對齊了沒。

這一個月讓我搞清楚的是：exit 0 描述的只是報告層。結果層是另外一件事，中間有一個不小的洞。🤣
