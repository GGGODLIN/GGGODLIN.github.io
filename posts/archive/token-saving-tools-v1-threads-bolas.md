最近脆上、GitHub 上一直冒出主打「省 token / 省 context」的工具，登 HN 高分、兩個多月發一百多版、社群裡傳「省 75% token」「省 96%」。我用 Claude Code 用得兇，額度跟錢都在燒，看到這種東西當然會手癢。所以這半個多月我前前後後裝了五個不同路線的：命令列代理、MCP server、輸出壓縮 skill、語意檢索 MCP，最後一個是上下文壓縮層 proxy。

省流：這五個我留了一個，而且留下來的那個原因根本不是省 token。

裝之前我以為差別只在「誰省得多」，裝完才知道完全不是這回事。第一個問題是省不了多少，宣稱跟實測常常差一個量級；第二個、也是更重的問題，是省下的那點要拿風險去換。

## 第一刀：報表上的省幅跟你帳單上的省幅，差一個量級

先講 RTK（Rust Token Killer），rtk-ai/rtk，Apache-2.0。路線是命令列代理：掛一個全域 PreToolUse hook，每次 Bash 都被攔下來，把輸出截斷、過濾再丟回去。官方對外講「常見開發命令省 60-90% token」，我裝的是 0.40.0。

它自己的報表 `rtk gain` 也很好看，試用第一天縮減率 73.5%，第二天穩態 30.8%，兩天平均 52.7%。問題是這個百分比算的是「砍掉多少 Bash 輸出」，不是「你帳單少了多少」。我拿 ccusage 對照真正送進模型的總量，1.5 天它在 957K input token 上幫我省下來的，攤到整個 13.72M input，真實只省了 7.0%；如果連 cache 建立的部分一起算，fresh 只剩 2.94%。換成錢，1.5 天大概省 2 到 4 鎂。

報表 52.7%、帳單 7%。這就是第一個要認清的事：工具報的省幅跟你在意的省幅，是兩個維度，常常差一個量級。

semble 也是同一套戲。它的 dashboard 自報省 96%（大概 1.4M token），但那個基準是「整檔讀進來」這種最浪費的讀法。我早期拉了一次 A/B 實測，開跟不開的成本是 4.06 鎂對 5.93 鎂，真實縮減大概 32%。外部 Show HN 上作者自己公開的數字又是另一個 98%，那是拿「grep 加 read」當基準算的。同一個工具，96、98、32 三個數字擺一起，從 96 掉到 32 差三倍。哪個是真的？對你帳單有意義的那個是 32。

## 真正的代價不在省多少，在賠多少

省不了多少還只是第一層。真正讓我把工具一個一個拔掉的，是它們省 token 的方式各自帶著不同的風險。

RTK 是有損截斷，而且是無聲的。`ps aux` 它幫我縮 98%，只留 CPU 跟記憶體最高那幾行；`rtk grep` 預設只回 200 筆、每行超過 80 字元就直接切掉，不會告訴你切了；`rtk ls -la` 大目錄縮 50 到 70%。最陰的是模型根本不知道自己少看了什麼。它連個「我截斷了」都不會回報，直接給你一份看起來完整的縮水版。出錯的時候不會跳紅字，是以「結論偏掉」「漏掉某個行程」「漏比對某一行」的形式出現，事後幾乎沒辦法歸因到「喔原來是工具偷砍了」。我做的東西容錯很低，這種無聲降級的風險，我賠不起。

順帶一提，RTK 那 161 次解析失敗它是 100% 回退原始輸出，這部分做得乾淨。但解析成功、確實截斷的時候，仍然有損。所以它最後試了 1 天 13 小時我就主動拔了。退役的理由很單純：省幅本來就薄，又會無聲降級，這對我太危險。先說清楚，它不屬於那種裝了沒人用的工具，是我用過之後嫌它危險才拔的。乾淨拔除、留了備份，設了四個重評條件。

context-mode 是另一種風險，裝了不穩定、燒資源。它是 MCP server，mksglu/context-mode，授權 ELv2、source-available。信任訊號做得很滿：登 HN 570 分、兩個多月發了 165 版（差不多每天兩個），上週 npm 兩萬筆下載；README 開頭一排 Microsoft、Google、Meta 的 logo，點下去才發現全是 `<a href="#">` 空連結，沒一個是真的。

它真正的問題是孤兒行程。裝著 5 天累積了 18 個孤兒，其中 2 對掉進空轉迴圈，各吃 98% 跟 99% CPU，整機飆到約 290%，熱保護開始降頻，耗電 1.27%/min（正常待機才 0.2 到 0.4%）。我把它移掉、`pkill -9` 之後，一分鐘 load average 從 10.29 掉回 4.81。除此之外它還掛著一票 open issue：任意檔案讀取沒有 deny policy、ctx_insight 字串插值的 shell injection、hook 過度刪 settings.json 把我別的 hook 砍掉、忽略 CLAUDE_CONFIG_DIR 打到多帳號。近乎每天發版，踩雷機率本來就高。我查的時候是這些 issue，狀態後來沒追，但這種發版節奏你自己心裡有數。

caveman 這個最有趣，它理論上最安全卻沒人用。它是 skill，壓的是 Claude 輸出端的措辭，丟掉冠詞、填充詞、客套，宣稱省 75%。我 5/30 把所有 jsonl 撈了一遍，被觸發 0 次，裝著從頭到尾沒叫起來過。原因也不難懂，它省的本來就只是單次回覆裡的虛詞客套，量級本就小，代價卻是改掉說話方式、犧牲對話深度。它自己 SKILL.md 裡甚至寫了一條 Auto-Clarity Exception：遇到安全警告、不可逆操作確認、多步驟序列怕被誤讀的時候，要暫時退出壓縮模式。工具自己都承認在這些情境壓縮會帶誤讀風險。

## 那換個「更該有效」的省法呢？也省不了多少

到這裡你可能會想，那是這幾個工具爛，換個方向砍呢？比方說別砍輸出，去砍常駐載入的東西，那不是更該有效？

我認真試著找這條退路。結果它在省 token、省錢這個維度上，連 RTK 那點 7% 都贏不了。

我把本機沒在用的 stdio MCP 從 13 個清到 6 個，`claude mcp list` 冷啟動從 10 秒多降到 7 秒上下，省了大概 4 到 15 秒。但這省的是啟動時間，不是 token。Claude Code 的 MCP tool 走 deferred pool，schema 要等 ToolSearch 才取，本來就不直接塞進 system prompt，所以清掉省的 token 趨近於 0（tool 名稱還是佔一點，但很少）。這些毫秒數都是量級估計，不是精確 benchmark。

唯一真的省到 prompt token 的，是控 always-on 的 skill 清單，那是實打實的常駐成本。我本機 78 個啟用的 skill 吃掉 6098 token。但這塊走 prompt caching，cache_read 大概只有 fresh 的十分之一價錢，就算砍一半，一天省個 0.2 到 0.4 鎂。比 RTK 那 7% 還少一個量級。（補一句口徑：官方 skill 清單預算預設是 `skillListingBudgetFraction=0.01`、`maxSkillDescriptionChars=1536`，我本機是自訂覆寫成 0.04 / 3072，前面那個 6098 token 是本機自訂值算出來的，不是 CC 預設。）

所以「換個更該有效的省法」這條退路也封死了。砍常駐載入，省 token 的天花板本來就低到這種程度。能省的空間就這麼大，那為了它去裝一個會無聲降級的工具，當然更不划算。

（唯一還算划算的省成本方向不在這條軸上，是把任務外包給更便宜的模型，那是另一篇的題目，這篇不展開。）

## 壓軸：headroom 把該做對的都做對了，我還是沒裝

前面四個多少有點「沒做好」可以挑。最後這個 headroom 不一樣，它是這五個裡最新的，也是我唯一親手裝起來 dry-run 量過效果跟資訊損失的，而且它把該做對的地方真的做對了。結論還是不裝。這個案例最值得寫。

headroom 是 chopratejas/headroom，定位「AI agent 的上下文壓縮層」，把 tool 輸出、log、RAG 結果、檔案、對話歷史在送進模型前先壓一道，宣稱省 60 到 95%，招牌數字是「省 90%」。兩萬多星等級、Apache-2.0、四種接法（當函式庫、當 proxy、包起來、走 MCP）。

先把公道給它，這很重要。它的核心招式 CCR 是透明可逆的。一大塊內容它不直接刪掉，而是搬到本地存好，原地留一張提貨單 `<<ccr:hash,size>>` 加上標題跟連結，模型看得到「這裡有東西、可以去領」，要用的時候自己呼叫 retrieve 把原文取回來。RTK 是直接刪行、模型壓根不知道少了什麼的無聲截斷，CCR 留了張提貨單，兩者完全是兩回事。在「透明還是無聲」這條軸上，headroom 明顯比 RTK 好一截。它是那種設計上有認真想過的工具。

那為什麼還是不裝？兩個原因。

第一個原因是它招牌那個高省幅，靠的根本是那顆 ML 模型，跟透明可逆的 CCR 沒什麼關係。我拿 47 筆真實的 tool 輸出，純當函式庫、零全域設定、用它自帶的 tiktoken 計數，親手 dry-run 了一遍。不開 ML，光靠那套結構化分流（原樣放行、無損整理重複結構、CCR 換提貨單），總共只省 15.6% 毛省。47 筆裡真正被壓的只有 9 筆，全集中在搜尋結果那類（壓到 64%），正在讀的 code 一個字沒動，0% 壓。這個 15.6% 攤到整個輸入流會更低，差不多又回到 RTK 那個量級。要衝到招牌的高省幅，必須開 ML（它叫 Kompress，是一顆 ModernBERT 抽取式編碼器，逐 token 打分、留高分丟低分，不是讀懂了改寫）。開了 ML，毛省衝到 69.7%，code 從 0% 壓到 80%，44 筆裡 43 筆掛上 CCR 提貨單。但代價是 inline 的內容被壓成「關鍵詞湯」，atom 存活率大概只剩 30%，dump 出來是斷頭句加行號碎片。所以 README 那個招牌「省 90%」，撐起來的是這顆 ML 模型，那張透明提貨單的功勞其實很小。

順帶說一句，這顆 Kompress 還換不掉。它寫死了 ModernBERT 的架構，你不能塞一顆通用 LLM、本地小模型或線上便宜 API 進去頂替。「不夠強就換一顆強的」這個直覺在這裡不成立。

而且要記住，dry-run 報的是毛省。真正的淨省等於毛省扣掉之後 retrieve 拉回來的那些 token。retrieve 拉得多就安全但淨省縮水，拉得少淨省接近毛省、但模型在拿著關鍵詞湯硬答，又繞回無聲誤讀。

第二個原因才是壓垮它的，而且不在壓縮品質，在整合架構。要走 proxy 那條接法，等於在 Claude Code 跟 Anthropic 之間的主動脈上擺一個代理層。這比 RTK 那種旁路 hook 重太多了：

- 它穿過你所有的流量，是單點故障。而且它遠不只一層薄薄的轉發，裡面塞了 FastAPI、預設要的 Rust core、CCR response handler、還有並發信號量。
- Max 帳號是用 OAuth 登的，proxy 轉址要原封不動把 OAuth bearer 轉過去，多數 proxy 預設是 API key 那套，弄不好第一天就把登入弄壞。
- 最尖銳的一點：它跟 prompt caching 本質互斥。壓縮會改掉 prefix，prefix 一變 cache 全 miss。你可能省了 15% 的 token，卻丟掉 90% 的 cache 折扣，在 Max 上算總帳是淨虧。
- 還有 transcript 分岔：Claude Code 的 jsonl 存的是沒壓的版本，模型實際看到的是壓過的，CCR hash 又只活在 proxy 的記憶體裡，重啟就變一串死 hash。

一個安全省只有 RTK 量級的工具，要我付這個整合風險，划不來。

最後 headroom 還逼我想通一件比這篇前面講的都更根本的事。我原本把「省 token」跟「資訊損失」當成兩件事，後來才發現它們根本是同一條軸。可逆壓縮為什麼能省？靠的就是「模型大部分時候不會回頭去讀原文」這個賭注。所以每省一個 token，都是賭模型不去讀被搬走的那塊內容，只有那塊真的是冗餘的時候才安全。「一百件只去領兩件」這種大省，只在清單型、掃過就丟的內容上成立，搜尋結果、log 就是這種，而那正好是 base 結構化路徑安全壓的那一類。ML 那個漂亮大數字，是硬把壓縮套到你正在用的內容上換來的（像正在改的 code），偏偏那裡最需要 retrieve、不去領的風險最高。再疊上 Claude Code 本來就會選擇性讀取（grep、分頁 read），加上 Max 既有的 prompt caching，能省的邊際比帳面還小。

所以「省很多又完全保真」本質做不到，除非省掉的本來就是冗餘。連 headroom 這種把透明可逆都做對、避開了無聲降級的工具，最後都因為「安全的省只有 RTK 量級，加上整合風險，又跟 caching 互斥」而被我退掉。連做對的都不值得裝，這就是「省 token 空間本來就小」最強的證據。

## 唯一留下來的那個，留它的原因不是省 token

五個工具我只留了 semble，而且我得老實講，留它跟省 token 一點關係都沒有。

前面說過它的省幅數字三個版本對不起來（96、98、32），這個工具在省 token 這個維度上既把數字講誇大、又量錯了維度。真正讓我留它的，是它能做 grep 做不到的事。

我手上有個專案後端是 ClojureScript、前端 TypeScript，前後端不同語言。grep 要搜得先知道確切的 symbol 名，而且要分語言各搜一遍。semble 走的是語意檢索，我用自然語言描述一個概念，它一次就把前後端兩邊相關的都撈出來。有一次我靠它撈出一個跨語言的命中，semble 找到、Read 確認、最後修掉一個篩選邏輯的 bug，進了一個 merged PR。另一次它幫我抓到一個字面上完全沒寫 retry 的延遲任務，grep 抓不到，它語意命中了。

省 token 對它來說只是副產品，它真正不可替代的是 grep 找不到的它找得到。反過來說這件事很清楚：省 token 從來就不是一個工具值得用的真正理由。（這個工具的採用率細節是另一篇的主題，這篇不展開。）

## 所以省 token 不該是你裝工具的理由

回頭看這一輪：

省不了多少，宣稱跟實測常差一個量級（RTK 報表 52.7% 對帳單 7%、semble 96% 對 32%、headroom 招牌 90% 對 base 實測 15.6%）。

省下的那點還要拿風險去換：有損工具是無聲降級（RTK 砍了事實、模型不知道漏了什麼），不穩定工具會燒機（context-mode 孤兒行程吃到 290% CPU），壓縮 proxy 要擺在動脈上、還跟 caching 互斥到可能淨虧（headroom）。

連退路都封死了：想換個更該有效的省法、去砍常駐載入，也贏不了 RTK 那 7%；連 headroom 那種把透明可逆都做對的工具，最後也因為安全的省太薄加整合風險而退掉。

而最深那一層是：省 token 跟資訊損失其實是同一條軸，可逆壓縮省掉的，就是模型賭它不會回頭讀的那塊。所以唯一被我留下來的 semble，我留它純粹因為它能做 grep 做不到的事，省 token 從頭到尾都不在理由裡。

裝工具之前先問自己：我到底在省哪一種成本、省得到多少、要賠什麼。多數時候答案是省得很有限、又要賠風險，那就別裝。真要省成本，等我那篇講「把任務外包給更便宜的模型」再聊。
