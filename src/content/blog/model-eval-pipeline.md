# 公開跑分脫離我的日常，於是我拿自己專案考 AI

每次新模型一發布，社群上的公開跑分榜就跟著洗版，但實際接進日常寫程式的 workflow 裡，體感跟榜單常常完全對不上。

原因其實很單純，公開排行榜離我的日常太遠了。它測的是乾淨孤立的標準題，答不出兩件我真正在意的事：第一，把這顆模型換進現有的 workflow 裡，會不會動不動就弄壞原本跑得好好的習慣跟規則；第二，把它丟進真實私有專案改程式碼或抓錯時，到底能不能直接上場。

既然外面的榜單回答不了，乾脆就用自己的規則跟 repo 來出題，做一套**專案耦合評測**。這條產線跑出來的最新成果，就是已經上線的公開[模型 Tier 表](https://blog.gggodlin.com/tier/)，公開頁上拆成「前沿表」跟「非前沿表」：前沿表收各家旗艦主力模型，非前沿表收輕量、免費或日常備援模型。以下要講的口徑跟數字，全部以截至 2026 年 11 月 25 日這份快照為準。

先講一個前提免得誤會。這份公開 Tier 表量測的其實是「模型加上當時 agent 外殼、推理設定與供應通道（例如官方 API、第三方聚合轉發或限免中轉）」的整合表現，跟把外殼全拆掉的純模型權重比較完全無關（換不同 agent 與第三方模型時帶來的條件限制，以前在[換第三方模型換到的是有條件的韌性](https://blog.gggodlin.com/blog/vendor-benefit/)提過脈絡）。整套產線跑出結果後，我最大的感想就是：要讓分數能看，千萬不能把所有失敗都算在模型頭上，「接線與供應壽命」「模型能力」「判官漂移」這三件事一定要分開量。

## 低成本快篩先過濾，能力、判官漂移跟供應壽命分軌記錄

新模型一接進來，產線不會直接拿昂貴的大題開考，而是先過兩段低成本閘門。第一段檢查基本接線跟最大輸出上限時，會先查過供應商契約裡的規格上限，再實際打端點驗證拿得到的真實上限，免得模型推理寫到一半被過小的上限截斷，結果被誤判成能力不足。

確認輸出上限參數沒被卡住後，系統才會往下跑 12 道自動快篩探針，專門測基礎執行異常：工具呼叫會不會卡死或正常收尾、繁體中文跟工具混用會不會出現亂碼或掉回簡體字、會不會忠實採信工具回傳的證據，以及該呼叫工具時會不會憑空硬答。每道探針都靠固定規則自動判出 `PASS`、`FAIL`、`N/A` 三種狀態，只要遇到請求層失敗或通道限流，一律標記為 `N/A`，不把通道卡頓混成模型能力差。

12 道快篩探針過關的端點，接著才會跑進階的前段考驗，看這顆模型在日常工作裡到底靠不靠譜：產線先拿 50 題日常短任務當基準，再搭配分析查證與真實工作負載的匿名盲評。

做到前段的真實工作負載盲評這關時，產線是找獨立的語言模型當匿名判官來打分數。我原本以為只要分數高就是模型變強、分數低就是退步，後來產線拿同一批舊答案重考對照，我才發現這群語言模型判官自己的給分尺度會漂移。當這一批判官集體變嚴格時，直接拿新分數去比過去存下來的歷史原分，連原本日常掛在線上的備援模型都會被誤判成大幅退步。為了解決單次評審的尺度漂移，產線在每段真實工作負載的評審包裡固定混入 3 份已經評過的舊答案當錨點，讓同一批判官在同一個包裡評完所有答案，最後只看同包內的配對差，這才把前段盲評的判官漂移抵銷掉，還原出真實的強弱排序。

至於供應壽命，則是在模型實際接上線後另外獨立記錄，不跟前段能力測驗混在一起。有些限免通道上的模型實力確實亮眼，曾經有一款模型在同包盲評裡明顯贏過原本日常掛在線上的備援模型，看起來很香，但限免入口一下架，接下來 24 小時內實際接進線上的兩條背景自動任務鏈送出去的 13,342 次請求全部 0 成功，只能立刻從自動路由模型池裡拔掉。部分限時免費或預覽方案本來就有到期日與資料訓練條款限制，這份公開 Tier 表只反映測試當下的表現，不代表它可以長久掛在產線上，更不適合把私有業務資料送進去。能寫對題跟能穩穩幹活，完全是兩碼子事 🤣。

## 拿真實私有專案的 PR 當考卷，再把盲審工具開源出去

12 道快篩探針跟前段的日常任務、真實工作負載都篩完，接下來才會進到核心實作考場：從真實私有專案抽取的 8 題真實 PR。這 8 題是前沿表與非前沿表共用的基準，考的就是模型在真實程式碼庫裡動手術的本事。

考場的設計核心就是隔離與盲審，每題分別看「測試通過數（原始／重算）」跟「匿名品質盲審（A／B／C）」兩個面向。所有隱藏測試跟標準正解都放在受測工作區外面，受測模型完全碰不到。隔離容器考完即銷毀，事後保留的是完整執行軌跡，腳本再從軌跡還原出改動差異、去掉模型身分後匿名打包，交給獨立的語言模型判官打出三個等級：A 代表直接採用、B 代表小修採用、C 代表需要返工。判官交回來的判定檔也要過一層格式與自洽驗證腳本，只要裡面列了阻斷級缺陷就必為 C，打了 B 或 C 也一定要附上具體引證，驗證不過或漏格就退回重跑，不直接納入榜單。

單看測試通過數的綠燈其實很容易被騙，自動化測試全過，不代表改動就能直接合併進主幹道。

有一款長視窗免費模型在其中一題把隱藏測試跑出 34/34 全過，單看測試報告漂亮得很（這種測試全綠但沒護住關鍵行為的毛病，以前在[AI 寫的測試全綠，但可能什麼都沒測](https://blog.gggodlin.com/blog/test-theater/)也寫過），但送進匿名品質盲審還是直接拿到 C 級阻斷。原因很簡單：它動手改程式碼時，順手把原本繁體中文的業務鍵名擅自改成了簡體字。功能雖然寫對了，合進去卻會直接弄壞既有資料結構，沒過盲審這關根本抓不到，也因此這款模型在現行非前沿表只落到最低的 T4 梯隊。

為了讓這套驗證邏輯不只鎖在私有環境裡，我把整套核心設計抽出來做成開源的 [repo-to-bench](https://github.com/GGGODLIN/repo-to-bench)（目前釋出 `v0.1.0`），將考場流程收斂成固定的六步指令鏈：建題時先驗證有 bug 的舊版測試必敗、已知正解必過，確認考卷有效；規劃後把整份測試計畫鎖成不可變雜湊，等操作者核准測試計畫雜湊才執行、開始動用模型額度；考完接著跑軌跡重建與匿名打包，最後進缺格退回的判定驗證。另外也附了零費用的合成煙霧測試，讓剛接手的人先跑通流程。

底層容器隔離執行後端接的是 [Harbor](https://github.com/harbor-framework/harbor)。這裡先講清楚邊界：`repo-to-bench` `v0.1.0` 目前是在 Harbor `0.22.0` 上完成驗證，不能直接等同支援上游最新發行版；另外它只負責建題、隔離跑完與打包驗證，不包含託管服務、自動呼叫判官或費用預算控管，供應商計價跟額度風險還是操作者自己要顧好。

## 前沿模型只看過題數拉不開差距，只好加考突變測試跟抓真 bug

上面那 8 題真實 PR 對分辨非前沿模型很有用，但一遇到頂尖的前沿模型，只看二元「全過／沒過」的過題數很容易黏在少數幾題內，常常彼此只差一兩條測試，甚至規格寫清楚的題目會一起撞頂，拉不開硬仗裡的可靠度差距。

這也是公開頁要拆成兩張表的原因：非前沿表看重日常任務、短任務耗時、8 題真實 PR，再加上由較強的前沿模型當主管拆解任務與驗收、受測模型當工人實際改程式的拆工驗收題（共用同一組 8 題真實 PR）；前沿表除了看 8 題真實 PR 的匿名品質盲審，再加考兩道更能拉開辨識度的關卡。

第一道加考是 3 題突變測試。產線挑出 3 題真實複雜模組，先讓模型對著原本的模組寫測試，考後再由 [Stryker](https://stryker-mutator.io/) 這類突變測試工具刻意製造一批改壞版本，檢驗模型寫的測試能抓出幾個。最後把 3 題各自的名次加總成綜合排名，取代只分過與不過的二元門檻，測試寫得扎不扎實一下就分得出來。

第二道加考是 6 份抓真 bug 考卷，合計 58 個真實 bug 版本，1 個版本 1 分、滿分 58 分。出題方式是把專案歷史上曾經修好問題的那筆修補拿掉，讓真實 bug 重現，請模型寫自動化測試抓出使用者看得到的異常行為。這關最花工夫的其實是人工逐條複核：有些測試表面上寫對了，實際上只去檢查內部狀態或旗標變化，根本沒驗證到使用者看得到的異常，這種命中只要經複核確認，全部退回不計分。

人工複核對最終結果影響非常直接。某款模型在這關原本自動統計拿下 50/58，剛好踩在前段門檻邊緣，逐條對照前面訂好的「只看內部狀態不算分」複核標準、退回 4 筆無效命中後，分數立刻掉成 46/58，從前段退到後段。不過這裡要老實交代一個限制：抓真 bug 以前在最早 2 份考卷重考 3 次時，前後兩群的分界非常一致；但擴充到目前這 6 份卷後，合計分數只有 `k=1` 單次有效作答，沒有六卷合計的重考證據，所以只能當成當下的單次實測來看。

## 從考場計分到公開上線前，先補齊這四道考場校準

整條產線跑久了就會發現，很多時候排行榜怪怪的，毛病其實出在考場本身量歪了，或是公開上線前的檢查沒卡緊。

### 題面缺口重算

先檢查隱藏測試裡是不是混進了題面規格書根本沒寫到的要求，害寫對規格的模型被扣分。做法很直白，把題面規格書跟每條隱藏測試案例逐條對帳，排除沒寫進規格的案例後重新算分。這一對照差很多：多款前沿模型原本只通過 3 題，排除題面缺口重算後直接拉開到 4 至 6 題。為了不粉飾過程，這份公開 Tier 表把 8 題真實 PR 的原始測試通過數跟重算測試通過數並列放上去，讓讀表的人兩邊都看得到。

### 重建環境與格式化工具重放

考後從執行軌跡重建程式碼改動時，原本的本機重放只模擬了檔案寫入動作，漏跑了模型透過指令呼叫的改檔腳本或格式化工具，判官才會對著沒跑工具造成的格式問題扣分。後來把重建步驟搬進隔離容器完整重放，再跟原始測試通過紀錄對帳，直接抓出兩類失真：有一題超過 80 欄的長行數，在補跑格式化工具後從 62 行降成 27 行，拆穿了原本不成立的格式扣分；另一次清查也抓出因為漏重放腳本改檔指令而產生的 5 份失效判定，全數作廢重評後才還原正常等級。這裡也把邊界講準：凡是當下已確認重放漏檔或重建失敗的汙損評審包，一律標註未評、不進這份公開 Tier 表；至於事後比對才抓出的格式化工具漂移，那一格換成新包後目前尚未重評，早期沒經過隔離容器重建的舊包也還沒全面清查，這仍是這份公開 Tier 表目前的已知缺口。

### 判官紀律與通道一致

匿名語言模型判官不能偷看評審包以外的檔案，同一輪評測的通道管理也不能中途失真。事後核對判官的工具呼叫紀錄時，只要發現讀了包外資料，該筆判定就直接作廢並重派乾淨重評；通道管理更直接影響整個考場的可比性，因為不同供應通道的推理設定生效狀況跟長輸出限制都可能不同，混走會讓各階段結果對不起來。再加上曾經發生過評測中途擅自綁死單一帳號，導致連續 12 場請求全遭拒絕、改回原本選定的輪替帳號池才全部順利跑完，因此現在一律在評測全階段固定同一條供應通道與路由方式，中途不隨意切換，也不把跨通道的作答耗時拿來硬比。

### 公開前去敏與版型無關驗收

公開資料上線前得確認沒有殘留公司名、私有專案名或內部題號，這部分直接寫進自動化契約測試，掃描資料檔攔截所有禁用字詞與題號。至於前端呈現，當初幫這份公開 Tier 表網頁做視覺改版時，先產出 9 個不同版面方案選型；為了避免舊的版面選擇器因為介面重排就誤報，驗收改用「資料檔裡的 207 段文句是否全數正確出現在渲染畫面上」逐條核對，不綁特定網頁元素結構，結果 9 版全部拿下 207/207 的完整對應。做到資料與呈現分離後，去敏契約測試也直接卡在發布前的自動閘門上。

## 三軸分帶怎麼切線，還有這份公開 Tier 表沒辦法保證的事

前沿表採用**三軸分帶**，三個項目的切線規則都寫在附註裡：8 題真實 PR 的匿名品質盲審（A／B／C）切成三段，拿到 4 題以上 A 進前段、其餘沒有 C 算中段、有 C 進後段；3 題突變測試綜合名次切成三段，第 1–3 名為前段、第 4–6 名為中段、第 7–9 名為後段；6 份抓真 bug 考卷因為每顆模型總分只考過 1 次、高分區分數緊黏，只切成兩段，50 分以上為前段、49 分以下為後段。分級時三項全進前段為 S 級，未滿三項前段、但三項都沒有後段為 A 級，任一項落入後段就是 B 級，同一個等級裡不排先後。

非前沿表則綜合日常任務、短任務耗時、8 題真實 PR 的測試通過數與匿名品質盲審，還有拆工驗收，由高到低切出 T1 到 T4 四個梯隊，再透過一列同時上兩張表的對照模型把刻度接起來（想看這套分級背後跟日常模型分工、多模型交叉審查的關聯，可以順手看[最強模型不是每件事都該用](https://blog.gggodlin.com/blog/model-routing/)跟[一個模型不夠：五軸交叉審的 code review 工作流](https://blog.gggodlin.com/blog/one-model-not-enough/)）。

方法講完了，該疊的甲也得疊好疊滿。讀這份公開 Tier 表或想拿這套邏輯去用之前，下面這幾條硬限制一定得先看清楚：

1. **每題只考一次**：8 題真實 PR、突變測試與抓真 bug 每題都是 `k=1` 的單次有效作答，不只同一個等級裡的小差距沒有統計穩定度，連落在等級切線邊緣的分數，重測一次也可能跟著換邊。
2. **切線對邊緣模型很敏感**：把成績切成 S、A、B 聽起來很乾淨，但只要移動分界線，名單就會跟著變。例如抓真 bug 的前段門檻只要從 50 分往上調到 52 分，原本踩在門檻邊緣的模型就會掉出前段，直接動搖 S 級名單。
3. **跨期條件與判官漂移不會消失**：8 題真實 PR 的匿名品質盲審是跨不同時間點逐批評審的，沒辦法每輪全數重包對評，因此語言模型判官的跨日尺度漂移仍無法完全消除。不同時期測的模型，環境條件也不會完全一樣；像非前沿表的拆工驗收就曾隨著模型換代切換過拆工主管版本，少數幾格的測試通過數跟匿名品質盲審甚至來自不同場次，或因重建不完整而空缺未評，讀這份公開 Tier 表時一定要對著附註一起看。
4. **公開頁只有現況快照**：已經換代的舊模型，以及測試期間曾以匿名代號上架、後來正式公開身分或換代的預覽模型，都會從這份公開 Tier 表上移出。公開頁呈現的是截至 2026 年 11 月 25 日當下的選型快照，歷史淘汰模型不會一直留在上面；公開頁下方掛的延伸閱讀，也只是補充方法論跟模型性格觀察，不代表同一批次考卷的原始報告。
