# 把工作流和模型徹底解耦，讓主力模型能隨時抽換

這半年主力模型跨版、跨代換得實在太快了，Claude 家族一路演進，Gemini 4 的 Pro 級主力也一路從 Argon、Carbon 換到 Neon，同時高速檔位也切上了 Hydrogen，幾乎每隔幾週底下的模型就已經不是同一批。

如果規則檔、subagent 定義跟 workflow 腳本全都直接寫死型號，每次換代就得把幾十份檔案翻出來重寫一遍，這套東西很快就會失真到沒人敢動。早期我還在效能規則檔裡寫過數十行針對特定舊型號的選型建議，結果模型一換代，整段建議當場作廢，最後直接砍掉重練。

我原本以為只要改用浮動別名就能一勞永逸，後來才發現這個想法太天真。Claude Code 版本更新把 `opus` 這個浮動別名改指 Claude Opus 5 當天，我本地一個字都沒改，也沒有手動切換模型，12 個 subagent 定義檔裡寫著 `opus` 別名的 6 個就這樣集體無聲換裝了。你人還坐在原地，底下的工程師半夜已經偷偷換過一批。

系列前面幾篇談過[配額逼我重劃 AI 分工](https://blog.gggodlin.com/blog/model-routing/)、接第三方模型遇過的[協議接線與視窗限制](https://blog.gggodlin.com/blog/cc-vendor-swap/)和[回報機制差異](https://blog.gggodlin.com/blog/protocol-model-dependency/)，也整理過怎麼拿自己的專案做[獨立評測產線](https://blog.gggodlin.com/blog/model-eval-pipeline/)。評測解決的是「挑哪顆模型」的問題，這篇要解決的是選好之後怎麼讓整套工作流換得動，而且不會一換就散掉。

後來我把整條接線拆成「工作角色 → 宿主槽位 → 邏輯角色群組 → 具體型號」四層抽象。接線耦合確實解掉了，但跑進真實工作流之後才看清楚，有三條治理邊界會直接穿透抽象層，沒處理好照樣出事。

## 先把規則裡的型號清乾淨，工作只綁認知責任

現在我的全域效能規則就只有一句話：主力模型交由我自己切換決定，規則裡面一律不釘任何模型名稱。

往下進到派工層，我改按任務本身不可省略的認知責任，拆出 3 類基本工作角色（實作、機械、判斷），再加上跨這三類疊加的「安全敏感」修飾標籤，最後落成 4 份獨立的通用角色定義檔。只要任務涉及憑證、權限、加密或漏洞修補這類防禦性安全工作，一律改派獨立的安全敏感角色定義檔。

這 4 份通用定義檔之外，幾份專職審查或探索的定義檔也全部比照辦理，把對應的模型槽位與推理深度集中鎖在各自檔案開頭設定區裡，直接對齊 [Claude Code Subagents 官方文件](https://code.claude.com/docs/en/sub-agents) 支援的宿主抽象槽位。這些槽位包含 `opus`、`sonnet`、`haiku`，以及對應高階旗艦的 `fable`；Workflow 腳本在呼叫端只許指定角色型別，不在腳本裡手抄型號或深度數值。

以前我也試過靠純文字規範，要求撰寫 workflow 腳本的 agent 自己填對參數，結果對照起來很直接：只要允許在 workflow 腳本裡手寫參數，3 個新寫腳本的 agent 全部跑去手抄數值，其中 2 個還漏寫推理深度，直接誤吃到當下 `session` 的預設值。單靠自律一定漂移，只能收進單一角色定義檔鎖死。

至於宿主槽位底下要接哪一顆模型，不設環境變數就會跟著官方版更浮動指向預設模型。一旦透過 [Claude Code Model configuration 官方文件](https://code.claude.com/docs/en/model-config) 提供的環境變數覆寫指向，槽位就從上游浮動指標變成自己控管的穩定介面，版更不會再半夜偷換。其中 `ANTHROPIC_DEFAULT_OPUS_MODEL`、`ANTHROPIC_DEFAULT_SONNET_MODEL`、`ANTHROPIC_DEFAULT_HAIKU_MODEL`、`ANTHROPIC_DEFAULT_FABLE_MODEL` 各自管四個明確槽位，`CLAUDE_CODE_SUBAGENT_MODEL` 則管未指定槽位時的 subagent 預設值。

我把這套啟動器封裝與環境變數映射整理公開在 [GGGODLIN/cc-vendor-bridge](https://github.com/GGGODLIN/cc-vendor-bridge) 裡。啟動器會透過 `ANTHROPIC_BASE_URL` 把請求導向後端的本機 API 轉發閘道，邏輯角色群組、備援順序與推理深度夾檔則跑在這個轉發閘道裡。

## 啟動器只認邏輯群組，底層換代只動本機轉發閘道

只有前面兩層還不夠，如果啟動器把底層模型 ID 直接塞進環境變數，每次換代還是得到處翻啟動腳本。

所以我把啟動器跟底層模型之間再切開一層：整場只走 Pro 或只走 Flash 的單一群組啟動器、混搭啟動器，以及非互動腳本與排程用的背景呼叫端，通通不直接指定具體型號，一律指向本機轉發閘道上的邏輯角色群組，像是 Pro 角色群組跟 Flash 角色群組。閘道上的群組層負責維護模型能力對應與成員清單，清單裡可以只排單一型號，也能排多個底層型號依序承接；至於單輪輸出上限（`CLAUDE_CODE_MAX_OUTPUT_TOKENS`），因為宿主對自訂模型名稱會套用保守預設，改由各啟動器依所屬群組各自帶上。

整條四層接線串起來大概長這樣：實作或機械角色走 `sonnet` 槽位，對應 Flash 角色群組，最後落在 Gemini 4 Hydrogen；判斷或安全敏感角色走 `opus` 槽位，對應 Pro 角色群組，最後落在 Gemini 4 Neon。

Gemini 4 家族這幾輪短週期連續換代，Pro 角色群組從 Gemini 4 Argon 換成 Gemini 4 Carbon、再換到 Gemini 4 Neon，Flash 角色群組切到 Gemini 4 Hydrogen，每次都只在閘道把群組成員換掉，外頭的單一群組啟動器、混搭啟動器跟背景呼叫端一行設定都不用改。

同一場 `session` 裡靠混搭啟動器做分工也很順：主控對話跟重推理槽位指向 Pro 角色群組，一般 subagent 槽位指向 Flash 角色群組，再由啟動器依群組帶上各自的輸出上限。走到這一步，抽換模型的接線成本基本上已經降到零了。

## 抽象層藏不住安全與把關落差，高速模型過了初試還是得停

接線雖然換得動，進到實戰最先撞上的，就是安全與把關紅線這第一條治理邊界。完全不能因為高速模型夠快、簡單測試過關，就把整個槽位換掉。

先前我評估過要不要把混搭啟動器的 `opus` 槽位，從當時底層跑著 Gemini 4 Carbon 的 Pro 角色群組，改映到當時底層跑著 Gemini 4 Hydrogen 的 Flash 角色群組。第一關考合規放水率快篩規則抽檢，專看模型能不能穩定抓出報告裡缺乏證據支撐的違規宣稱；Hydrogen 這關確實過了，速度也快了一大截，但進到第二關深度稽查跟保密測試就立刻踩線停損，最後還是把 `opus` 槽位留回給 Pro 群組。

當時跑出來的對照結果很直接：在合成憑證外洩檢查裡，我拿 3 段含模擬金鑰與驗證碼的對話切片（三題分別埋了 1、2、3 組模擬憑證，合計 6 組）交給模型做稽查報告，看它會不會違規抄出原值；結果 Carbon 0/3 外洩，Hydrogen 卻在埋了 2 組與 3 組的那 2/3 題裡把 5 組原值直接抄進報告。另一場 40 段深度對話雙盲稽查也一樣，我把兩顆模型各自審查 40 段對話缺陷的匿名報告混在同一份評分包裡，交給獨立判官盲評，再去比對既有缺陷清單的召回率（參考命中率），Hydrogen 比 Carbon 少了約 15 個百分點。這種差距靠在 `prompt` 多加幾句禁令是補不平的。

而且這條紅線不只怕模型太鬆漏放秘密。另一面，過去把安全敏感角色鎖在重推理槽位，也曾假設這樣就能避開模型內建安全分類器管太嚴、把正當防禦性安全檢測誤判成攻擊而拒答的路徑；但新一代主力與重推理模型（Claude Opus 5.5 與 Sonnet 5.5）同樣已經啟用安全分類器，所以不管防外洩還是防誤拒，這類前提每次大改換代都得重驗，不能寫進定義檔就一勞永逸。

所以面對速度跟底線的兩難，底線不能單靠提示自律去賭。我的做法是先讓涉密與正式審查角色在定義檔裡鎖死對應 Pro 群組的 `opus` 槽位，再靠混搭啟動器的兩段純提示分流，把高速模型用在對的地方。啟動時會附加系統提示，引導主模型把前段探索與一般實作優先派給 Flash 槽位，同時明令後段終審與涉密審查禁止覆寫降配。

另外靠啟動器掛載的 `SessionStart`（`compact`）hook，在每次對話自動壓縮後把分流規則重新注入尾端防遺忘；事後再拿執行紀錄核對有沒有漂移，真的發生漂移才升成硬擋。排除其他不同入口的場次後，單看這套混搭啟動器的統計，高速模型 subagent 佔比從 baseline 約 15%–22% 升到 54.9%，同時涉密席誤降跟憑證原值外洩皆為 0。

## 同一把金鑰底下留舊代備援，只會把請求送回高誤攔現場

第二條得守住的同金鑰備援隔離，同樣會直接穿過這四層架構。邏輯角色群組雖然支援多成員順序備援，但有一條鐵律我寫進了路由原則：絕對不把「同一把 API 金鑰、同一家供應商的上一代舊模型」排進第二順位當靜默降級備援。

原因很簡單，在同一個共用金鑰池跟同一家供應商底下，配額限流和服務波動往往會連動發作，更麻煩的是舊代 Gemini 4 Argon 本身就被上游內容安全過濾頻繁誤攔。Pro 角色群組剛切給 Gemini 4 Carbon 的初期，原本還在同金鑰第二順位掛了 Argon，結果只要 Carbon 稍微遇到限流或短暫波動，請求就會掉進誤攔率高出百倍以上的舊代現場。

後來我拍板移除同金鑰的舊代備援，改由 Carbon 單獨承接，真出錯就交給重試機制或跨帳號路徑，而不是靜默掉回舊代。對照切換前舊代 Argon 當主力的數萬筆真實流量紀錄，上游內容安全過濾誤攔直接減少 99.4%。

這裡把邊界講清楚：不降級原則禁止的是「同一把 API 金鑰、同一供應商內降級舊代」以及主模型或審查席的靜默降級。如果是同一個模型換不同供應商帳號作備援，或是經過明確拍板的跨供應商帳號、跨模型家族多級背景備援鏈，則不在禁止範圍內；這類多級背景備援鏈限定用在非互動、不碰憑證的批次背景管線（例如離線整理或摘要），本來就不涵蓋主模型、涉密席與正式審查席。

## 啟動器後綴會蓋掉宿主設定，推理深度只能留給單一入口管

至於第三條推理深度控制權，出事的地方往往藏在啟動器傳出去的字串上。很多啟動器習慣在送往本機轉發閘道的模型名稱後面寫死 `:high`、`:medium` 或括號強度（例如 `模型名(high)` 或 `(max)`），看起來好像很省事，其實是把整個解耦架構從背後架空。

我核對過本機轉發閘道的實作與單元測試，模型名稱後面附帶的深度後綴，解析優先序就是高於請求本文裡帶出來的深度參數。只要啟動器還留著寫死後綴，不管在互動介面怎麼切 `/effort`，或是各個工作角色定義檔裡配好什麼 `effort`，送到閘道那一刻全部失效。

最後我把單一群組與混搭啟動器的寫死後綴全面拔除，把推理深度的控制權真正還給宿主和角色定義檔。底層各代模型支援的檔位不一樣，這部分交給閘道依模型支援表自動夾檔到最近合法值就好：例如請求 `max` 時，送到最高支援 `xhigh` 的 Gemini 4 Neon 與 Hydrogen 會自動夾成 `xhigh`，送到只支援到 `high` 的 Argon 時則自動夾回 `high`，也就不會因為跨代不支援該檔位而直接撞上游 400 錯誤。

不過宿主這裡還有一個很容易忽略的連動行為。只要在 Claude Code 互動介面執行 `/effort` 並確認套用，宿主就會依實際傳給閘道的模型鍵（例如 `group/gemini-pro`），把深度值寫進個人設定檔的 `modelSettings` 裡。從那一刻起，該模型鍵就不再跟隨全域 `effortLevel` 預設值，連帶影響之後新開與非互動場次，所以調完不要以為只作用在當下那一個 `session`。至於各工作角色定義檔裡明確寫死的 `effort`，優先序仍高於 `session` 層預設，除非被環境變數 `CLAUDE_CODE_EFFORT_LEVEL` 硬蓋 🤔

## 防住三種靜默漂移，並保留只影響下一輪的單場逃生開關

四層抽象和三條邊界立起來之後，日常會慢慢腐壞這套系統的，主要就是「漂移」。上線這段時間實際撞見過三種漂移：

1. **散落寫死**：總有些角落檔案偷偷寫死了舊型號。對不走單一邏輯群組、跨工具共用型號字串的模型家族，我改維護一份集中版本表，加上一份使用登記表標記各處狀態（讀表＝動態讀版本表、手改＝格式無法讀變數須手動補、固定＝刻意鎖舊版對照或相容、停用＝已下線），再配自動化掃描工具定期巡檢。但靜態掃描只能抓字面寫出來的模型與群組名稱，看不到執行期動態拼出來的字串，也抓不到上游在同一個模型 ID 背後做的靜默更新，請求層的實際解析紀錄還是得盯。
2. **雙寫不同步**：為了避開下面會提到的長對話異常區間，單一群組與混搭啟動器兩度下調了 Gemini Pro 的自動壓縮視窗（也就是對話累積到多少 token 就自動觸發壓縮的門檻）；結果獨立維護同一組參數的互動選單入口，第一次就出現延遲同步，第二次才刻意手動對齊。能讀同一份集中參數，就千萬不要兩邊各自手寫。
3. **周邊監控漏認**：我有一個同時顯示即時燈號並提供單場切換開關的終端機狀態列外掛，會依近期請求的卡住比例與負載亮燈，提醒適不適合開新對話，過濾規則會同時比對群組名與底層型號關鍵字。Pro 群組換成 Gemini 4 Neon 之後，過濾規則卻還停在舊關鍵字、沒把 `neon` 補進去，靠群組名稱送進來的請求還能間接算到，但評測腳本、刻意保留的退路入口或單場暫切這類直連具體型號名的請求就會整個漏算。

至於單代模型在長 context 區段出現的局部異常，我的處理原則一樣是不放寬全域同金鑰備援。實戰用量紀錄顯示，Gemini 4 Neon 在 300K 以上長 context 的純思考空回（模型把額度全花在內部思考、卻輸出零字正文）比率為 2.01%，大約是 Carbon 同期 0.05% 的 40 倍；不過一旦逼近 800K，連切回 Carbon 一樣救不回來，整批輸出直接純思考空回。

針對這種只發生在單代模型中段長 context 的異常，我在終端機狀態列外掛保留了一個單場逃生開關：它掛在宿主每個回合送出請求前的 hook 上，按下去只會把沒有 `agentId` 的當前 `session` 主模型下一輪請求改寫為上一代 Carbon，凡是帶 `agentId` 的 subagent 請求一律直接放行，不動全域群組也不影響其他 `session`。第四節禁的是閘道自動靜默降級，這裡則是人工按需、限縮在單一對話主模型的受控例外。

當然這裡要主動疊甲，把話講實：這個單場暫切開關只能應付單代模型在中段長 context 的偶發異常，沒辦法突破整個模型家族共有的 800K 物理上限，治本還是得提早觸發壓縮。而且調降自動壓縮視窗來減少撞進 300K 以上異常區的機會，跟撞到時手動改跑 Carbon 的單場暫切開關，兩件事同時跑在同一段觀察窗裡；目前樣本還不夠拆開證明單場開關每次按下都能讓空回對話恢復正常正文輸出，還不能宣稱已經 100% 救回。

## 解耦省掉的是接線成本，換代前還是得進考場

四層解耦能消除的只有「換模型就得翻修工作流與規則」的接線與改檔成本，它不會自動替你判斷模型夠不夠格，更不能取代換代前的獨立能力評測與換代後的行為複驗。哪顆模型該坐哪個槽位，依然要靠真實考卷與實戰表現說話，現行各型號的位置可以對照本站公開的[模型 Tier 表](https://blog.gggodlin.com/tier/)。

同時，只要上游還會對模型做無聲更新，只看設定檔就一定會失明：平常要觀測實際解析出來的底層模型 ID，用來抓浮動別名是不是被悄悄改指；同時追蹤日常真實工作的錯誤率、空回率等實戰紀錄，才能發現同一個模型 ID 背後行為悄悄改變。而為某一代模型臨時加上去的權宜參數，一定要維持可回退，不能讓單代補丁慢慢沉澱成永久規則。

最後我把這套架構收斂成五條換代檢查標準，每次要換主力或角色模型就照著跑一輪：

1. **規則零寫死**：確認常駐規則檔與 workflow 腳本只寫工作角色與抽象槽位，沒有散落具體模型版本號，且通過靜態掃描。
2. **單一真源與雙寫對齊**：換代只動本機轉發閘道群組或集中版本表，同時對齊各啟動器與互動選單入口上的輸出上限與自動壓縮視窗。
3. **安全與把關紅線實測**：重推理與涉密把關席在降配或換代前，先拿含保密檢查與深度稽查的對照題跑過；沒過線就留守 Pro 群組，只把前段探索與實作分流給高速模型。
4. **備援跨帳號隔離**：檢查同把 API 金鑰與同一供應商底下沒有掛著舊代模型當靜默降級備援，故障切換改走不同供應商帳號或經明確拍板的跨家備援鏈。
5. **深度控制權與周邊觀測同步**：拔掉啟動器會蓋過宿主 `/effort` 與角色定義檔的寫死後綴，並確認閘道會自動夾檔。同時同步更新狀態列燈號與實際解析模型 ID 的過濾規則，只為突發異常留一個限縮在單一對話下一輪的受控逃生開關。

照這套架構跑下來，平常換代已經不太需要翻動工作流了，不過單場逃生開關跟提早壓縮視窗拆開計算的救回紀錄還在繼續收樣本，哪天真被實測證偽要重調，大概又得再修一輪狀態列外掛了🤣
